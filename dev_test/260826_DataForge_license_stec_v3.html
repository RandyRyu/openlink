00

판정 요약

Executive

두 문서는 같은 문제 인식에서 출발해 서로 다른 층위를 풀었다. 기획 초안은 무엇에 값을 매길 것인가(과금 대상·서비스 분류·가드 항목)를, 개발 문서는 얼마를 받을 것인가(지표·산식·등급표·실측)를 답했다. 두 문서는 대체 관계가 아니라 상하위 관계이며, 개발 문서의 요금 산식은 재계산 결과 8개 등급 전부 정확히 재현된다. 통합의 실제 과제는 가격이 아니라 계측 기준의 충돌 3건과 기획 초안이 요구한 가드 4종의 반영 여부다.

요금 산식 검증8 / 8등급 전부 산식과 일치 · 보정 불필요
지표 정의 충돌3건계측 지점 · 과금축 · 보존기간
기획 요구 미반영4종가드 항목 전부 개발 문서에 없음
의사결정 대기8건§09 · 경영 승인 3건 포함

결론 4문장

  • 골격은 개발 문서를 채택한다. 기본료 2,000만원 + 일일 수집량 구간 등급(430,000원/GB·day) 구조는 산식·실측·어뷰징 방어까지 완결되어 있고, AS-IS의 Tag/Column 이중 등급이 낳은 3대 병폐(수량 감축 노동, 의견 충돌, 필요 데이터 미수집)를 구조적으로 제거한다.
  • 기획 초안의 가드 4종을 L2 계층으로 신설해 얹는다. 일일 증분 하나로는 초당 부하·가상 태그 연산·전송량·쿼리 스캔이 전혀 잡히지 않는다. 단, 가드는 과금축이 아니라 상한선으로만 둔다(@김성만 원안 유지).
  • 계측 기준을 이원화해 두 문서의 충돌을 해소한다. 청구 근거는 BigQuery 논리 증분(투명·재현 가능), 우회 탐지는 Kafka 처리량(대조 전용). 어느 한쪽을 버리는 대신 역할을 나눈다.
  • 가격 수준 자체는 경영 판단이 남아 있다. AS-IS 최대 청구 구간(월 8,500만~1억 2,300만) 대비 세아 실측 기준 To-Be는 월 5,000만원으로, 손익분기 고객사 수가 약 1.7배로 늘어난다(§08).

AS-IS 개선 포인트 달성 점검

기획 초안 §1.3.1이 제시한 개선 포인트 3개는 통합안에서 모두 달성된다. ① 수량 체크·증명 노력 → BigQuery SQL 자동 판정으로 소멸. ② 체계 단순화 → 이중 등급이 단일 축으로. ③ 의견 충돌 요소 제거 → 태그 동일성 판단이 과금과 무관해짐. 다만 §1.3.1의 4번(운영 공수가 섞인 라이선스가 과다청구로 보임)은 개발 문서가 기본료에 운영 서비스를 다시 포함시키면서 재발 위험이 있다 — L0의 인보이스 분리 표기로 대응한다.

02

수치 검증 결과

Verification

개발 문서의 등급표·실효단가·실측치를 전부 독립 재계산했다. 요금 산식은 8개 등급 전부 정확히 재현된다. 반면 가드값 산정 방식과 태그 단가 환산에는 보정이 필요한 지점이 있다.

실효단가 열의 정의 주의

개발 문서의 "GB/day당 실효단가" 열(400,000~440,000원)은 기본료를 제외한 수집 사용료만 대표점으로 나눈 값이다. 고객이 총 청구액으로 역산하면 위 표의 총액 실효단가(DF-80 기준 714,286원)가 나오며, 이 값은 소량 → 대량으로 갈수록 단조 감소해 볼륨 디스카운트가 일관되게 성립한다. 반면 수집 사용료 기준 실효단가는 DF-20(400,000) → DF-60(440,000) → DF-130(426,087)으로 비단조라, "왜 130 등급이 60 등급보다 GB당 싸냐"는 반박을 부른다. 내부 문서에서 두 열의 정의를 분리 표기하고, 협상 테이블에는 총액 기준만 쓴다.

보정 필요 ① — 가드값 산정 기간 의존성

"상위 10개 평균"은 측정 기간에 따라 엄정도가 6배 달라진다. 62일 관측에서 상위 10개는 상위 16.1%지만, 1년 계약이면 상위 2.7%다. 기간이 짧을수록 상위 10개가 분포의 넓은 부분을 포함해 평균이 중앙값 쪽으로 끌려 내려가고, 결과적으로 짧은 측정 구간일수록 가드값이 낮게 잡혀 VNTG에 불리하다. 세아의 62일 관측이 정확히 그 구간이다.

보정안

가드값 = 유효 측정일 상위 3%의 평균, 단 최소 5일 · 최대 20일로 정의한다. 62일 → 상위 5일, 182일 → 상위 5.5일, 365일 → 상위 11일이 되어 계약 기간과 무관하게 일관된다. 대외 문서에는 "상위 구간 평균"으로만 표기하고 산식은 계약서 부속에 둔다. 세아 케이스는 이 정의로 재계산해 등급 변동 여부를 확인해야 한다(원자료 필요).

추가 검증 지적

대상문제권고
태그당 단가 환산 "1,000tag 기준 약 3,700,000원 → 태그 1개당 월 3,715원". 3,700,000 ÷ 1,000 = 3,700원으로 기재값과 불일치(3,715원은 미반올림 3,715,000원 기준). 더 근본적으로 1,000 태그 → 8.6 GB/day라는 환산 전제가 문서 어디에도 없다(역산 시 태그당 8.6 MB/day). 환산 전제(태그당 일일 바이트, 수집 주기, 페이로드 크기)를 명시하거나, 대외 자료에서 태그 환산 논리를 아예 제거한다. 태그 단위 환산은 폐기하려는 AS-IS 축을 되살리는 역효과가 있다.
용어 일관성 §1.1은 "고객에게 저장 GB로 환산해 보여준다", §3.3은 "대내외 표현을 저장량이 아닌 수집량 과금으로 통일"로 서로 어긋난다. "일일 수집량(GB/day)" 단일 용어로 확정. 저장 용어는 보존기간 항목에서만 사용.
가드 용어 "상위 10개 평균 = 가드값"은 실제로는 상한(cap)이 아니라 과금 기준값이다. @김성만이 말한 가드(초당 처리량 밴드)와 같은 단어를 쓰고 있어 회의에서 혼선이 반복된다. 과금 기준값(Billing Base)과 가드(Guard/Cap)를 용어로 분리. 본 설계서는 이 구분을 따른다.
밴드 폭 비대칭 하위 밴드는 폭 20 GB/day, 상위는 30~40으로 넓어진다. 세아의 63.6은 60~80 밴드의 하단이라 상단 80까지 16.4 GB/day가 추가 과금 없이 열려 있다(단가 환산 약 705만원/월 상당). 영업적으로는 "무중단 확장 여유"로 제시 가능하나, 수익 누수 폭을 인지하고 협상 시 명시적 가치로 청구한다. 밴드 폭 축소는 단순화 취지에 역행하므로 권하지 않는다.
비례성 주장 "40 GB/day 17,200,000 → 80 GB/day 34,400,000, 정확히 2배" — 재계산 결과 사실. 단 이는 대표점이 아닌 실제 GB/day 기준이며, 기본료 포함 총액은 2배가 아니다. 비례성 증명은 수집 사용료 한정임을 반드시 병기. 총액 비례를 주장하면 즉시 반박당한다.
03

통합 라이선스 체계 — 5계층

Architecture

두 문서의 모든 과금 요소를 다섯 개 계층과 하나의 범위 밖 항목으로 배치한다. 각 계층은 서로 다른 질문에 답하며, 계층이 섞이는 순간 AS-IS의 "이게 무슨 비용인지 모르겠다"는 문제가 재발한다. 청구서는 이 계층 순서 그대로 라인 아이템을 분리한다.

L0
Base — 최소 기본료
DF-Stream · DF-Port 소프트웨어 사용권(IP) + 상시 운영지원(설치·구축, 장애 대응, 문의 대응, 정기 업데이트·보안 패치, 매뉴얼 제작·배포). 데이터 저장·서비스 이용 여부와 무관하게 부과되는 최소 유지비.
사업장당 월 20,000,000원
청구서에 ① 솔루션 사용권 ② 운영지원 서비스 2줄로 분리 표기하되 번들 필수(분리 구매 불가). 다사업장 정책은 §09-③ 미결.
L1

대표점 × 430,000원/(GB·day)
DF-20 ~ DF-200 8단계. 기본 보존기간 12개월 포함(신규 보정안). 200 초과는 Enterprise Custom.
L2

일일 증분이 잡지 못하는 부하·비용을 상한선으로 포착한다. 초당 수집 피크, API 전송량, 가상 Tag/스케줄러 동시 실행 수, DW 쿼리 스캔량, 보존기간. 초과가 곧 청구가 아니라, 지속 초과 시 상위 등급 전환 또는 해당 플러그인 활성으로 이어진다.

L3

저장량과 상관없이 가치를 만드는 고부가 기능. 소재 ID 트래킹·매칭, 외부 시스템 연계·API 전송, AI·LLM, ML·예측, 확장 백업·복구, 통합 관제. 쓰는 모듈만 부과하므로 그룹사 간에도 "이 계열사는 트래킹만"으로 공정·명확하다.

Standard/Pro/Enterprise 티어는 폐기(그룹사 맥락에서 등급 차별이 어색). AI·ML은 별도 규칙(§06).
L4

밖

GCP 프로젝트를 고객이 소유·관리하고 청구서도 고객이 수령한다. BigQuery 스캔·slot·egress·VM 등 인프라 비용은 전량 고객 부담.
고객 직접 계약
compute 어뷰징 우려가 구조적으로 소멸. 락인 없음은 그룹사 협상의 강력한 세일즈 포인트.
왜 L0의 인보이스를 쪼개는가

AS-IS 이슈 §1.3.1-4는 "운영 공수가 포함된 라이선스 비용이 과다청구로 보인다"는 고객의 최초 요청이었다. @이재훈·@김성만 두 사람 모두 라이선스와 운영비 분리를 주장했으나, 개발 문서는 기본료 2,000만원을 "솔루션 사용권 + IP + 지속 투입 인력 서비스"의 묶음으로 다시 통합했다. 총액을 지키면서 요청을 충족하는 해법은 계약 분리가 아니라 청구서 라인 분리다. 금액 협상 여지를 열지 않으면서 투명성 요구는 만족시킨다.

기본료 명목 변경에 대한 예상 반박

AS-IS에서 기본료 2,000만원은 "인프라비 확보" 명목이었다(기획 초안 §1.1). To-Be에서 인프라를 고객 GCP로 넘겼는데 기본료가 그대로면 "인프라는 우리가 내는데 기본료는 왜 그대로냐"는 반박이 필연적이다. 개발 문서 §3.6이 이에 대한 답("인프라료는 당신이 내는 게 맞고, 우리가 받는 것은 그 데이터를 수집·저장·활용 가능하게 만드는 소프트웨어 사용권이다")을 준비해 두었으나, 명목이 언제 왜 바뀌었는지를 협상 전에 문서로 정리해 두어야 한다. 계약 갱신 시점에 AS-IS 계약서와 나란히 놓이면 즉시 드러난다.

미해결 — 과금축의 성격 (flow vs stock)

@김성만의 원안은 논리적 볼륨 = 수집 데이터포인트 × 보존기간이라는 재고(stock) 개념이었다. 개발 문서가 채택한 일일 증분은 흐름(flow)이다. 개발 문서 §3.3은 이 부작용을 스스로 인정한다 — "보존기간이 다른 두 고객이 같은 일일 증분이면 총 저장량이 크게 달라도 요금이 동일". 위의 "기본 보존 12개월 포함 + 초과 시 저장 확장" 보정은 이 구멍을 실무적으로 메우지만, 과금축의 성격 자체를 바꾸지는 않는다. flow 축을 유지할지, stock 축으로 되돌릴지는 §09-①의 의사결정 사항이다. flow 축의 장점은 청구액 안정성(증분이 flat이라 "매년 무한 상승" 문제 없음)이고, stock 축의 장점은 실제 원가와의 정합성이다.

L2 — 가드 밴드 (신설)

일일 증분 하나로는 네 종류의 비용이 전혀 잡히지 않는다. 기획 초안의 Action Item ①~④가 정확히 이 구멍을 지적했고, 개발 문서에는 대응 항목이 없다. 가드는 과금축이 아니라 상한선이며, 초과가 곧 청구가 되지 않는 것이 핵심이다 — 그래야 고객이 수집 주기를 늘리는 건강한 절감 행동에 페널티가 붙지 않는다.

동시 실행 수		 가상 Tag의 CPU 연산 부하는 저장량과 무관하다. "1초 주기로 복잡한 SQL 연산을 하는 가상 태그 100개면 VM이 마비된다"(기획 초안 Action ②). 등급별 동시 실행 가능 가상 Tag 연산 / 배치 스케줄러 Plugin 개수 제한. 도커 단위 Plugin 추가 구매. 안 쓰는 가상 태그 삭제를 유도하는 건강한 통제(@유성열 의견 반영).
G4 DW 쿼리 스캔량
조건부		 BigQuery는 저장보다 대시보드 새로고침 쿼리 스캔 비용이 훨씬 크다. 가드가 없으면 대시보드를 잘못 짠 고객 때문에 인프라 비용이 폭증한다(기획 초안 Action ④). 계정당 월 1TB 스캔(초안 제시값). compute가 고객 GCP인 계약에서는 미적용 — 비용이 고객에게 직접 나가므로 자연 억제. VNTG 계정 운영 계약에만 적용, 초과 시 MSP Bypass 청구.
G5 보존기간 같은 일일 증분이라도 보존기간이 2배면 총 저장량이 2배다. 개발 문서 §3.3이 자인한 결함. 기본 12개월 포함. 최소 보존기간 미만 설정 불가. 12개월 초과 보존 요청 시 저장 확장 요금(L3).
밴드 구체 수치는 인프라 실측 후 확정 대상(§10 로드맵 P2). 본 표는 가드 항목과 처리 로직을 확정한다.
왜 throughput을 1차 과금축으로 쓰지 않는가

@변중환의 지적 — "자원 사용량 기반은 일부러 사용량을 늘릴 수 있으니 객관적이지 않다". throughput을 1차 과금축에 놓으면 이 우려가 살아난다. 저장량(증분)을 1차 축에 두고 throughput은 가드로만 두면, 고객이 수집 주기를 늘렸을 때 throughput과 저장량이 함께 내려가는 일치된 레버가 되어 부풀릴 인센티브가 생기지 않는다. 이것이 @김성만 ②-가드의 설계 의도이며 통합안이 그대로 계승한다.

AI · LLM — 기획 초안의 10% 방식은 채택 불가

기획 초안은 AI 서비스를 "DF 라이선스 계약 금액의 10% 추가"로 처리했다. 이 방식은 런타임 토큰 비용을 전혀 잡지 못한다. 기존 플러그인 공식(기본료 + 개발 공수)은 일회성 R&D 비용만 잡는데, LLM은 개발이 끝난 뒤에도 매 호출마다 추론 비용이 계속 발생한다. 이 구조가 방치되면 고객이 무거운 AI 기능을 상시 돌려도 VNTG는 개발비만 받는다. VNTG 마스터 키로 대납하는 구조는 금지 — 그 순간 토큰 비용이 VNTG 손실이 되고 마진이 고객 프롬프트 습관에 인질로 잡힌다.

ML · 예측 — 도메인 리스크 (내부 경고)

철강 배치 공정(제강 등)은 범용 시계열 모델 가정과 근본적으로 불합치한다(TimesFM 커버리지 40~50% 수준, 80% 아님). "이상 탐지·예측"을 표준 플러그인 정찰가로 팔면 안 되는 이유다. 이 계열은 반드시 공정 검증을 포함한 맞춤 개발로만 제공하고, 대고객 문서에도 "공정 특성 사전 검증 후 적용"으로 명시한다. 기획 초안의 "인프라 비용 20% 추가" 방식은 이 리스크를 가격에 반영하지 못한다.

정당한 비용 통제 — 허용 · 권장

수집 주기 연장, 미사용 데이터 삭제, 보존 기간 단축(최소 기간까지), 수집 중단은 모두 허용하고 적극 안내한다. AS-IS의 병폐는 고객이 등급을 넘기지 않으려 필요한 데이터까지 안 받았던 것이다. 통합안에서는 절감 레버가 데이터 필요성이 아니라 수집 설계에 걸린다.

보정 — 절감 반영 시점의 비대칭 조정

개발 문서는 "감축은 현재 계약 요금이 아니라 다음 계약 갱신 시 가드값에 반영"으로 정했다(전향식). 정산 절차를 없애는 장점이 있지만, 고객이 절감 노력을 해도 당해년도에 아무 효과가 없다는 뜻이다. @유성열이 준비한 "비용 절감 방안 안내"가 실효를 잃고, AS-IS 이슈 3(필요 데이터 미수집)이 다른 형태로 재발할 수 있다.

권고 — 비대칭 조정. 하향 조정은 계약 중간(6개월 시점) 연 1회 재산정을 허용하고, 상향은 다음 갱신에만 반영한다. 영업적으로 "절감 노력은 6개월 안에 요금에 반영됩니다"라고 말할 수 있게 되며, 상향이 늦게 걸리므로 VNTG 리스크도 제한적이다.

신규 조항 — 두 문서 모두 공백

  • 지원 범위 선긋기. 기본료 포함 지원은 장애 대응·문의 대응·정기 점검으로 한정한다. 교육·트레이닝은 문서·계약에서 기본 포함 항목으로 명시하지 않는다 — "교육"을 명시하면 무제한 교육 요청이 상시 유입된다(실제 발생 중). 심화 교육·온보딩 세션·워크숍은 L4 유상 전문 서비스로 분리해 SOW에 명문화.
  • 계측 오류 정정 절차. 스냅샷 누락·SQL 오류·GCP 장애로 인한 계측 왜곡 발생 시 정정 기준과 소급 범위. 두 문서 모두 없음.
  • SLA. 수집 가용성 목표, 데이터 손실 시 책임 범위, 최소 수집 주기 보장. 고객이 절감을 위해 주기를 늘릴 때 품질 하한을 어디에 두는지 함께 정의.
  • 단가 에스컬레이션. 다년 계약 시 KOSA SW기술자 평균임금 공표 단가에 연동한 인상 조항. 기본료가 인력 서비스를 포함하므로 인건비 상승이 직접 마진을 침식한다.
  • 중복 데이터 책임 이관. DW/DM 단위의 데이터 중복 판단과 책임은 사용자(고객) 측에 있음을 명시. 운영자가 중복을 policing하지 않는다 — AS-IS 이슈 2(태그 동일성 의견 충돌) 재발 차단.
대외 노출 금지 항목

다음은 협상 테이블에 절대 올리지 않는다. ① GB/day당 실효단가(43만원/GB) — 노출되면 고객이 초정밀 종량 정산 협상으로 끌고 간다. ② M/M 원가와 인건비 산정 근거 — "투자 회수 끝나면 내려주냐", "M/M이 실제 그만큼 드느냐"는 원가 검증 논쟁으로 흘러간다. ③ 선투자 회수 논리 — 가격의 근거이되 정당화 논리는 가치여야 한다. 앞에는 가치·단순함·통제·투명성을 세운다.

해석

To-Be 체계로 전환하면 손익분기에 필요한 고객사 수가 약 1.7배로 늘어난다. 이것이 반드시 잘못된 결정이라는 뜻은 아니다 — AS-IS 체계는 고객이 필요한 데이터를 안 받는 방향으로 대응하게 만들어 계정 성장 자체를 막고 있었고, 단순·투명한 체계는 신규 그룹사 확대 속도를 높인다. 다만 "몇 개 계열사를 몇 년 안에 확보한다"는 확장 계획이 이 인하폭의 전제이므로, 그 계획과 함께 승인받아야 한다. 8단계 무중단 확장 구조도 이 관점에서는 고객 성장에 따른 자동 증액 경로라는 매출 논리를 갖는다.

09

미해결 쟁점 — 의사결정 요청

Decisions

통합 과정에서 해소되지 않은 8건. 각 항목의 결정 주체와 권고안을 함께 표기했다.

1
1차 과금축을 flow(일일 증분)로 확정할 것인가
@김성만 원안은 논리적 볼륨 = 데이터포인트 × 보존기간(stock). 개발 문서는 일일 증분(flow). 본 설계서는 "증분 + 기본 보존 12개월 포함"으로 봉합했으나 과금축의 성격은 그대로다. 권고 — flow 유지. 청구액 안정성과 SQL 자동화 완결성이 결정적이며, 보존기간 구멍은 L1 포함 기간과 G5 가드로 실무 봉합 가능하다.
체계 근간팀 합의
2
AS-IS 대비 인하폭과 확장 계획을 승인할 것인가
세아 AS-IS 실제 등급 확인이 선행 조건. BEP 고객사 수가 약 1.7배로 늘어나는 만큼, 목표 계열사 수·확보 시점과 묶어 승인받아야 한다.
경영 승인
3
다사업장 기본료를 어떻게 부과할 것인가
창원 + 군산처럼 한 고객사가 복수 사업장을 운영할 때 기본료 2,000만원 × N인가, 감면인가. @김성만 ①은 "사업장당 Base", 개발 문서 §4는 business_place_mt 단위 명시. 권고 — 사업장당 부과 원칙 + 2번째 사업장부터 감면율 적용(운영 규모의 경제 반영). 감면율 수치 결정 필요.
영업 · 팀
4
BI · 대시보드를 기본 제공으로 둘 것인가
개발 문서는 기본 제공(기본료 정당화의 가치 앵커), @김성만 ③은 df-port 기능 모듈 과금 대상. 권고 — 기본 제공 유지. 기본료 2,000만원이 "무엇에 대한 값인가"를 설명할 수 있는 가장 눈에 보이는 자산이고, BI를 떼면 기본료 방어가 IP 주장 하나로 얇아진다.
팀 합의
5
라이선스와 운영비를 어느 수준까지 분리할 것인가
@이재훈·@김성만은 분리 주장, 개발 문서는 기본료에 통합. 권고 — 계약은 번들 유지, 청구서 라인만 분리. 계약을 쪼개면 고객이 운영비만 재협상하려 들고, 라인만 분리하면 투명성 요구는 충족된다.
팀 합의
6
가드값 산정 기간 정규화안을 채택할 것인가
"상위 10개 평균" → "상위 3%(최소 5일·최대 20일) 평균". 채택 시 세아 62일 원자료로 재계산해 등급 변동 여부를 먼저 확인해야 한다(상위 5일 평균이 80을 넘으면 DF-100으로 이동).
개발 · 팀
7
신규 고객 첫 해 기준값을 어떻게 산정할 것인가
전향식은 직전 계약 기간의 실측을 쓰지만 신규 고객은 실측이 없다. 개발 문서는 "예상 증분으로 초기화"만 언급. 설계 태그 수 기반 추정치의 근거, 실측 확보 후 재정산 시점과 소급 여부를 확정해야 한다.
개발 · 영업
8
태그당 단가 환산 논리를 유지할 것인가
"태그 1개당 월 3,715원" 기재값이 본문 금액(3,700,000원 ÷ 1,000)과 맞지 않고, 1,000 태그 → 8.6 GB/day라는 환산 전제가 문서에 없다. 권고 — 대외 자료에서 제거. 폐기하려는 AS-IS 태그 축을 되살리는 역효과가 크다. 내부 참고용으로만 남기되 전제를 명시.

협상 앵커 — 월 5,000만원이 담는 것

수집량(GB)은 시장에서 가장 싼 커모디티 지표다(AWS SiteWise 등 GB당 센트 단위). 실효를 역산한 고객에게 "1.9TB/월 수집에 왜 월 5,000만원이냐"는 반박은 예정되어 있다. 지표가 가치를 나르지 못하므로 문서가 가치를 날라야 한다.

담고 있는 것구체 내용시장에서 따로 사면
철강 도메인 IP행안부·산업부 기반 표준 용어 사전(word/term), ISA-95 계층, 값·업무 도메인 체계, RFM 등 설비 표준컨설팅 + 구축 수억원, 재현 난이도 극상
데이터 거버넌스SSOT 파이프라인(DB 단일 원천), 데이터 리니지 자동화, 표준-현업 용어 매칭, RBAC/컬럼 마스킹별도 거버넌스 솔루션 라이선스
운영 · 지원 서비스설치·구축, 상시 기술지원·장애대응, 정기 업데이트·보안패치, 매뉴얼상시 전담 인력 M/M 비용
8단계 무중단 확장현재 등급 상단까지 추가 비용 없이 수집 확대, 등급 상향만으로 스케일—
플랫폼 기능BI 대시보드, 모니터링, 카탈로그, 통합검색, 게시판, 사용자 관리개별 BI/모니터링 툴 각각 구독
 "따로 사면" 열은 개략적 앵커링용. 구체 금액은 협상 상황에 따라 제시하며 과도한 수치 확약은 금지.

협상 스크립트 — "수집량이 아니라 위 다섯 가지 묶음에 값을 매긴다. 특히 철강 표준 사전과 소재 트래킹 기준 데이터는 현업과 함께 수년간 만든 자산으로, 시장에서 재현하려면 컨설팅·구축비가 별도로 든다. GB 단가로 환산하지 말고 대체 조달 비용과 비교하라."

본 문서는 두 원본 문서(DF 라이선스 체계 수립 기획 초안 2026-06-21 · DataForge 라이선스 요금 산정 근거)의 내용을 대조·검증해 통합한 내부 확정용 설계서다. 요금 산식·실측치·AS-IS 등급표의 수치는 원본에서 인용 후 독립 재계산으로 검증했으며, 검증 판정과 보정안·미해결 쟁점은 본 문서의 분석이다. 원가·M/M·실효단가·선투자 관련 내용은 대외 노출 금지. 세아창원특수강 AS-IS 실제 등급, 가드 밴드 실측 수치, 상위 3% 재계산 결과는 아직 확보되지 않은 값이며 §10 로드맵의 선행 과제다.
