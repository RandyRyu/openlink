Overview
01 · 개요

DF-Stream(수집/운영자 관리)과 DF-Port(고객사 사용자 서비스)를 모두 구축·제공하는 경우의 비용 체계. 배포 방식(Edge/Cloud)별 과금 철학을 구분하고, 기존 태그·컬럼 카운트 기반 과금 방식의 주의사항과 권장 통합 모델을 함께 정리한다.

핵심 명제 — 비용 항목은 Edge·Cloud 공통이며, 달라지는 것은 각 항목의 과금 철학(CapEx vs OpEx)이다. 또한 과금 단위(태그·컬럼 카운트)는 라이선스 뼈대로는 적절하나, 단가 분리·데이터셋 기본료·주기 밴딩·종량 오버레이로 보정해야 왜곡이 사라진다.
Edge 구축형On-Premise

고객 사이트에 서버를 구축하고 Package를 설치·제공. 고객 자산화(CapEx) 중심. 폐쇄망·보안 민감·대규모 단일 고객에 적합.

CapEx · 영구라이선스 + SI + 유지보수
Cloud 구독형Managed K8s

클라우드 Kubernetes 위에 Package를 배포·제공. 구독(OpEx) 중심. 빠른 시작·탄력적 확장·PoC에 적합.

OpEx · 구독료 + 사용량 종량
Common Frame
02 · 비용 5축 프레임 (공통)

배포 방식과 무관하게 비용은 다음 5개 축으로 분해된다. 이후 섹션에서 각 축의 과금 방식을 Edge·Cloud로 구분한다.

1

플랫폼 라이선스 — DataForge 자체 SW 사용권

DF-Stream + DF-Port 소프트웨어 사용권. VNTG 매출의 핵심 축.

2

인프라 (Infra)

서버·컴퓨팅·스토리지·네트워크. 배포 방식별 차이가 가장 크게 발생하는 축.

3

구축/설치 (Implementation)

일회성 초기 구축 공수(man-month). 현장 SI 여부에 따라 차이가 큼.

4

운영/유지보수 (O&M / Support)

패치·업데이트·모니터링·장애대응·SLA. 정기 발생.

5

종량 요소 (Usage / Metered)

BigQuery, 데이터 처리량·보존 등 외부·사용량 기반 변동 비용.

💡
스택 대부분이 OSS(NestJS·Next.js MIT / PostgreSQL·TimescaleDB·Kafka·Keycloak Apache 2.0 / Valkey BSD)이므로 ①번 축의 SW 라이선스 원가는 거의 없다. 대신 KEPServerEX(상용)와 BigQuery(종량)가 별도 원가로 작동한다.
Model A
03 · Edge 비용 체계 — CapEx 구축형

영구(Perpetual) 라이선스 + 현장 구축(SI) + 연간 유지보수 모델. 고객 자산화 중심.

5축과금 방식
① 라이선스영구 구축 단위 1회 판매. 규모(공장 수·태그 수·컬럼 수)별 에디션 티어링.
② 인프라고객 부담 서버 직접 구매. 우리는 사양 가이드 + 설치만 제공.
③ 구축비일회성 · 높음 현장 방문, OT/IT 망분리, 방화벽 정책, Kafka 3노드 HA, 단계적 설치.
④ 유지보수연 15~22% 라이선스가의 일정 비율. 원격지원·패치·장애대응.
⑤ 종량고객 직접/대행 BigQuery 사용 시 GCP 종량제는 고객 직접 계약 또는 대행 매입.
Edge 비용 흐름
초기 (1회) : 영구 라이선스 + 구축 SI + (KEPServer·Windows 매입) │ ↓ 매년 (정기) : 유지보수 (라이선스가 × 15~22%) │ ↓ 변동 (사용) : BigQuery 종량 (선택) → 고객 직접 정산 ─────────────────────────────────────────────── 성격 : CapEx 중심 · 초기 투자 큼 · 이후 고정 유지비
⚠️
Edge 고유의 숨은 원가 — 스택 대부분은 무료 OSS지만, KEPServerEX(Kepware)는 상용 라이선스이고 OT 수집 서버에 필수다. Windows Server 라이선스도 동반된다. 두 항목은 Edge 견적에서 반드시 별도 라인으로 명시해야 한다.
Model B
04 · Cloud 비용 체계 — OpEx 구독형

월/연 구독료 + 사용량 종량 모델. Helm 차트 배포로 구축을 자동화해 초기 비용을 낮춘다.

5축과금 방식
① 라이선스구독 월/연 구독료. 사용 규모에 연동.
② 인프라종량 vCPU·RAM·Storage·Network 사용량. 우리가 배포 후 재판매(markup) 또는 고객 클라우드 계정에 배포.
③ 구축비일회성 · 낮음 Helm 차트 배포 자동화. 온보딩 비용 수준.
④ 유지보수구독 포함 SaaS형으로 구독료에 포함. 또는 별도 매니지드 옵션.
⑤ 종량사용량 반영 데이터 처리량·스토리지·BigQuery를 사용량 그대로 청구.
Cloud 비용 흐름
초기 (1회) : 온보딩 (Helm 배포 · 낮음) │ ↓ 매월 (구독) : 플랫폼 구독료 (티어별) + 유지보수 포함 │ ↓ 변동 (사용) : 인프라 리소스 + 데이터 처리/보존 + BigQuery ─────────────────────────────────────────────── 성격 : OpEx 중심 · 초기 투자 작음 · 사용량 비례 변동
Metering
05 · 과금 단위 (Metering Dimension)

규모와 가격을 연동할 측정 단위. 기존에는 태그 수(시계열)와 레거시 데이터셋의 컬럼 수를 과금 단위로 사용해 왔다. 이 단위를 표준화하면 견적·티어링이 일관된다.

단위설명 / 비용 연동성
공장/사업장 수 핵심1 Factory = 1 Kafka Connect Task 격리 원칙 → 비용과 가장 직접 연동.
수집 태그 수 기존OPC UA 수집 Tag count. 고빈도 시계열(예: 892 태그 → 일 2,500만 건).
레거시 컬럼 수 기존MES/L2/ERP 데이터셋 테이블의 주요 컬럼 수(ColumnSpec 기준). 주기적 배치 수집.
데이터 처리량 / 보존msg/s, GB/day, 보존기간. 인프라 사이징·종량의 핵심.
DF-Port 사용자 계정 수고객 서비스 좌석(seat) 규모.
활성 Stream / Pipeline 수Benthos Stream·데이터셋(토픽/커넥터) 개수.
➡️
태그·컬럼 카운트 방식은 직관적이고 감사 가능하지만, 단독·평면 합산 시 왜곡이 생긴다. 다음 섹션(06)의 주의사항과 권장 통합 모델(07)을 함께 적용해야 한다.
Cautions
06 · 과금 방식 진단 — 태그·컬럼 카운트 주의사항

태그 수 + 컬럼 수 기반 과금은 라이선스 단위로는 적절하나, 그대로 단순 합산하면 아래 4가지 구멍이 생긴다.

결론 — 카운트 기반은 라이선스 뼈대로 유지하되, ① 태그·컬럼 단가 분리 ② 데이터셋 기본료 ③ 주기 밴딩 ④ (Cloud) 종량 오버레이로 보정해야 한다.
1

태그 ≠ 컬럼 — 단위 등가성 문제

태그는 독립 신호 스트림(한계비용 실재). 반면 한 테이블의 컬럼들은 같은 row·INSERT로 함께 적재되어, 테이블 내 컬럼 1개 추가의 한계비용은 거의 0.

→ 태그 단가 = 컬럼 단가로 두면 컬럼 과대·태그 과소 책정. 단가를 분리해야 한다.

2

수집 주기·보존 누락 — 진짜 비용 동인

100 태그 @100ms ≠ @10s (데이터·스토리지·컴퓨트 수십~수백 배 차이). 컬럼도 매분 vs 매일 수집이 비용 차이가 큰데, 카운트는 동일하다.

→ 같은 카운트의 두 고객이 인프라 부하가 전혀 달라 마진 노출. 주기·보존을 반영해야 한다.

3

파이프라인 고정비 누락

데이터셋(테이블) 1개 = Kafka topic·Connect sink·Benthos stream 각 1개 (컬럼 3개든 30개든 동일). 1 Factory = 1 Connect Task.

→ 데이터셋당 고정비가 큰데 컬럼 수로만 과금하면 이 고정비가 안 잡힌다. 데이터셋당 기본료 필요.

4

"주요 컬럼" 정의의 모호성

누가 "주요"를 정하느냐가 분쟁·협상 표면이 된다.

→ ColumnSpec(컬럼명·자료형·PK·NOT NULL·제약)이 이미 파싱되므로 "수집 대상 컬럼 전체" 또는 "PK + 측정컬럼"처럼 객관 규칙으로 고정 권장.

한계비용 비교 — 카운트가 놓치는 지점
태그 1개 추가
실재
테이블 내 컬럼 1개 추가
≈0
데이터셋(테이블) 1개 추가

테이블 내 컬럼 한계비용은 낮지만, 새 데이터셋(테이블)을 추가하면 토픽·커넥터·스트림 고정비가 발생한다. 컬럼 수보다 데이터셋 수가 더 강한 비용 동인이다.

Recommended Model
07 · 권장 통합 과금 모델

태그·컬럼을 같은 단가로 더하지 말고, 라인을 분리하고 보정 인자를 넣는다. 이렇게 하면 06의 4가지 왜곡이 사라진다.

통합 과금 공식
총액 = 플랫폼 기본료(티어) + 태그 요금 [ 태그 수 × 태그단가 × 주기밴드 ] + 데이터셋 요금 [ 데이터셋당 기본료 + (컬럼 수 × 컬럼단가) × 주기밴드 ] + (Cloud 한정) 데이터량·보존 종량 오버레이 ─────────────────────────────────────────────── 핵심 원칙 : 컬럼단가 < 태그단가 · 데이터셋당 기본료로 파이프라인 고정비 회수
라인별 과금 구조
라인과금 구조핵심 보정
태그태그 수 × 태그단가 × 주기밴드(≤1s / 1–10s / >10s)빈도 차이 반영
데이터셋(레거시)데이터셋당 기본료 + 컬럼 수 × 컬럼단가(태그단가보다 낮게) × 주기밴드(실시간/시간/일)고정비 + 컬럼 한계비용 차이
종량(Cloud)처리량(GB) · 보존기간 사용량빈도·보존 어뷰징 차단
Edge 적용

고객이 인프라를 소유 → 빈도·보존이 우리 원가가 아님. 카운트 기반이 라이선스 capacity 단위로 적절("태그 N개 + 컬럼 M개까지").

  • 현행 카운트 방식 거의 그대로 유지
  • 데이터셋당 기본료만 추가해 파이프라인 고정비 보강
Cloud 적용

우리가 런타임 원가를 부담 → 카운트만으론 위험. 빈도·보존을 올리는 고객에서 마진이 샌다.

  • 카운트 + 데이터량·보존 종량 오버레이 필수
  • 주기밴드로 고빈도 고객 가격 상향
✅
한 줄 정리 — 카운트 기반은 라이선스(특히 Edge)의 뼈대로 좋다. (a) 태그·컬럼 단가 분리, (b) 데이터셋당 기본료, (c) 주기 밴딩, (d) Cloud 종량 오버레이 — 이 4가지를 더하면 평면 합산의 왜곡을 막는다.
Edition Tiers
08 · 티어 구성 제안

동일 측정 단위를 양쪽에 적용해, Edge는 티어별 영구 라이선스 가격표, Cloud는 티어별 월 구독가로 패키징한다.

티어규모 가이드Edge 과금Cloud 과금
Starter단일 공장 · 소규모 태그/컬럼 · PoC영구 라이선스 (소)월 구독 (소)
Standard복수 공장 · 중규모 · 운영 본격영구 라이선스 (중) + SI월 구독 (중) + 종량
Enterprise대규모 · HA · 폐쇄망 · 전사영구 라이선스 (대) + SI + SLA월 구독 (대) + 종량 + 매니지드

티어 경계는 공장 수 · 태그 수 · 데이터셋(컬럼) 수를 1차 기준으로, 데이터 처리량·계정 수를 보조 기준으로 둔다. 상위 티어로 갈수록 HA·SLA·매니지드 운영이 포함된다.

Hybrid
10 · 하이브리드 모델

수집·OT 연동 특성상 DF-Stream(수집)은 Edge에, DF-Port(고객 조회/시각화)는 Cloud에 두는 절충안. 동국제강 같은 폐쇄망 제조 고객에 현실적이다.

하이브리드 배치 + 과금
Edge 측 : DF-Stream (수집/운영) → 폐쇄망 내 구축 과금 : 구축비 + 영구/연 라이선스 + 유지보수 │ ↓ (정제 데이터만 외부 전송) Cloud 측 : DF-Port (고객 조회/시각화) → 클라우드 구독 과금 : 월 구독 + 종량 (데이터/스토리지/BigQuery) ─────────────────────────────────────────────── 혼합 과금 : "Edge 구축비 + Cloud 구독" 결합 설계
  • OT 데이터는 폐쇄망 밖으로 나가지 않으면서, 고객 셀프서비스(조회/마트 생성)는 클라우드 확장성 확보
  • 구축비 부담은 수집 측에 한정, 고객 서비스는 OpEx로 분산
