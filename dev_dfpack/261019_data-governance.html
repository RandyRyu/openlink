데이터 거버넌스 쉽게 이해하기

작성일 2026-10-19

데이터 거버넌스는 '회사 데이터를 누가, 어떤 규칙으로, 어떻게 믿고 쓰게 할 것인가'를 정하는 일입니다. 이 문서는 데이터 전문가가 아닌 사람도 읽을 수 있도록 8개 장으로 나눠 설명합니다.

한 줄 비유: 데이터 거버넌스는 도서관 운영 규칙입니다.

도서관 데이터 거버넌스
책 상태 점검(찢어진 페이지, 오탈자) 데이터 품질
열람실 출입증, 귀중본 서고 잠금 데이터 보안
도서 목록 카드(제목, 저자, 분류번호) 메타데이터
이 책이 어느 출판사에서 와서 누가 빌려갔는지 기록 데이터 Lineage(계보)
관장, 분야별 사서, 서고 관리인 CDO, Steward, Custodian
한국십진분류법 같은 표준 DAMA-DMBOK, DCAM 등 프레임워크

책이 아무리 많아도 목록이 없고, 상태가 엉망이고, 누가 관리하는지 모르면 아무도 그 도서관을 쓰지 않습니다. 데이터도 같습니다.

1. 데이터 거버넌스 정의와 필요성

데이터 거버넌스 = 데이터에 대한 권한·책임·규칙을 정하고, 그것이 지켜지는지 감독하는 체계입니다. 데이터를 직접 다루는 일(저장, 변환, 분석)은 '데이터 관리'이고, 거버넌스는 그 관리가 올바르게 굴러가도록 방향을 잡는 '운영 규칙과 심판' 역할입니다.

DAMA-DMBOK이 말하는 거버넌스

DAMA-DMBOK(Data Management Body of Knowledge)은 데이터 관리 분야의 대표 참고서입니다. DMBOK은 데이터 관리를 11개 지식 영역으로 나누고, 그 한가운데에 데이터 거버넌스를 둡니다(Snowflake). 나머지 10개 영역은 바퀴살처럼 거버넌스를 중심으로 연결됩니다.

DMBOK 11개 지식 영역 쉬운 말로
데이터 거버넌스 (중심) 전체 규칙과 책임을 정함
데이터 아키텍처 데이터가 놓일 전체 설계도
데이터 모델링·설계 테이블과 관계를 그리는 일
데이터 저장·운영 DB를 안정적으로 돌리는 일
데이터 보안 누가 볼 수 있는지 통제
데이터 통합·상호운용 시스템 간 데이터 주고받기
문서·콘텐츠 관리 비정형 문서, 파일 관리
참조·마스터 데이터 고객, 제품, 코드값의 '정답본' 관리
데이터 웨어하우징·BI 분석용 저장소와 보고서
메타데이터 관리 데이터에 대한 설명서 관리
데이터 품질 데이터가 정확하고 믿을 만한지 관리

현재 표준은 DMBOK 2판이며, AI 거버넌스와 클라우드 환경을 반영한 DMBOK 3.0이 2027년 발간을 목표로 개발 중입니다(DATAVERSITY, DAMA International).

왜 필요한가: 거버넌스가 없을 때 생기는 일

증상 현장에서 들리는 말 거버넌스가 주는 해법
같은 지표가 부서마다 다름 "영업팀 매출이랑 재무팀 매출이 왜 달라요?" 용어·지표 표준 정의(비즈니스 용어집)
데이터를 찾을 수 없음 "그 데이터 어디 있는지 아는 사람?" 데이터 카탈로그, 메타데이터
오류의 원인을 모름 "대시보드 숫자가 갑자기 튀었는데 어디서 잘못된 거죠?" Lineage(계보) 추적
책임자가 없음 "이 테이블 누가 관리해요?" Owner·Steward 지정
유출·규제 위반 위험 "개인정보가 분석 서버에 그대로 있네요" 분류·접근통제·마스킹
AI 결과를 믿을 수 없음 "이 모델 무슨 데이터로 학습했어요?" 학습 데이터 출처·품질 관리

핵심은 거버넌스의 목적이 통제가 아니라 안심하고 쓰게 하는 것이라는 점입니다. 규칙이 명확하면 사람들은 매번 허락을 구하지 않고도 데이터를 빠르게 쓸 수 있습니다.

2. 핵심 4기둥 - 품질, 보안, 메타데이터, Lineage

거버넌스가 실제로 관리하는 대상은 네 가지로 요약됩니다. 각각 다음 질문에 답합니다: 믿을 수 있나 (품질), 안전한가 (보안), 무엇인지 아나 (메타데이터), 어디서 왔나 (Lineage).

① 데이터 품질 - "이 숫자 믿어도 되나?"

품질은 '용도에 맞게 쓸 수 있는 상태'를 뜻합니다. 보통 아래 차원으로 측정합니다.

품질 차원 뜻 예시 (설비 센서 데이터)
완전성 빠진 값이 없는가 전력량계 값이 10분간 비어 있음
정확성 실제 값과 맞는가 실제 220V인데 2,200V로 기록
일관성 시스템 간 값이 같은가 MES와 ERP의 생산량이 다름
유효성 규칙·형식을 지키는가 온도 칸에 문자열 'ERR' 저장
적시성 필요할 때 최신인가 실시간 대시보드가 3시간 지연
유일성 중복이 없는가 같은 설비가 두 개 코드로 등록

② 데이터 보안 - "아무나 보면 안 되는 데이터는?"

보안은 데이터를 분류하고, 등급에 따라 접근을 통제하는 일입니다.

  • 분류: 공개 / 내부 / 기밀 / 개인정보 같은 등급을 붙임
  • 접근통제: 역할(RBAC)이나 속성(ABAC) 기반으로 권한 부여, 최소 권한 원칙
  • 보호 기술: 암호화, 마스킹(홍길동 → 홍*동), 가명처리, 행·열 단위 보안
  • 감사: 누가 언제 무엇을 조회했는지 로그로 남김

③ 메타데이터 - "이 데이터가 뭔데?"

메타데이터는 '데이터에 대한 데이터', 즉 설명서입니다.

종류 담는 내용 예시
비즈니스 메타데이터 의미, 정의, 담당자 "가동률 = 실가동시간 ÷ 계획가동시간"
기술 메타데이터 스키마, 타입, 위치 pc2.power_meter.kwh DOUBLE
운영 메타데이터 적재 시각, 건수, 실행 이력 매일 02:00 적재, 1.2M rows

메타데이터를 모아 검색할 수 있게 만든 것이 데이터 카탈로그이고, 비즈니스 용어를 표준화한 것이 비즈니스 용어집 (Glossary)입니다.

④ 데이터 Lineage(계보) - "이 숫자는 어디서 왔지?"

Lineage는 데이터가 원천에서 최종 보고서까지 어떤 경로와 변환을 거쳤는지 기록한 족보입니다.

전력량계(OPC-UA) → 수집 서버 → Raw 테이블 → 정제(단위 변환) → 집계 테이블 → 에너지 대시보드

Lineage가 있으면 두 가지가 쉬워집니다.

  • 영향도 분석(앞으로): "이 컬럼을 바꾸면 어떤 대시보드가 깨지나?"
  • 원인 분석(뒤로): "대시보드 숫자가 이상한데, 어느 단계에서 틀어졌나?"

테이블 단위보다 컬럼 단위 Lineage가 더 정밀하며, OpenLineage 같은 오픈 표준으로 여러 도구의 계보를 한곳에 모을 수 있습니다.

3. 조직과 역할 - Owner, Steward, Custodian, CDO

거버넌스는 도구보다 사람과 책임이 먼저입니다. 핵심 원칙은 "모든 중요한 데이터에는 이름이 붙은 책임자가 있다"입니다.

아파트에 비유하면

역할 아파트 비유 하는 일 보통 누가 맡나
CDO (Chief Data Officer) 관리사무소장 전사 데이터 전략 수립, 거버넌스 위원회 주관, 예산·우선순위 결정 임원급
Data Owner (소유자) 집주인 데이터의 최종 책임, 접근 승인, 품질 기준과 보존 기간 결정 해당 업무 부서장 (예: 생산팀장)
Data Steward (관리인) 반장·동대표 용어 정의, 품질 규칙 작성, 이슈 처리, 현업과 IT 사이 통역 업무를 잘 아는 실무자
Data Custodian (수탁자) 경비·시설관리 저장, 백업, 권한 설정, 암호화 등 기술적 운영 IT·인프라·데이터 엔지니어
Data Consumer (사용자) 입주민 규칙에 따라 데이터를 찾아서 활용, 문제 발견 시 신고 분석가, 현업, AI 개발자

가장 흔한 혼동은 Owner와 Custodian입니다. 서버를 운영하는 IT팀(Custodian)이 데이터의 '주인'이 아닙니다. "이 데이터를 누구에게 공개할지"는 업무 책임자(Owner)가 정하고, IT는 그 결정을 기술로 구현합니다.

거버넌스 조직 구조 (일반형)

  1. 데이터 거버넌스 위원회: CDO와 주요 부서장. 정책 승인, 분쟁 조정, 투자 결정
  2. 데이터 거버넌스 사무국(DGO): 표준·정책 문서화, 교육, 성과 지표 관리
  3. 도메인별 Steward 그룹: 생산, 품질, 설비, 영업 등 업무 영역별 실무 관리
  4. 기술 운영 조직: 플랫폼, 카탈로그, 보안 도구 운영

운영 모델 3가지

모델 특징 장점 단점
중앙집중형 중앙 팀이 모든 규칙과 운영을 담당 일관성, 빠른 표준화 병목, 현업 이해 부족
분산형 각 부서가 자율적으로 관리 현업 밀착, 속도 부서마다 기준이 달라짐
연합형 (Federated) 중앙은 공통 규칙, 도메인은 실행 균형, 확장성 역할 조율이 필요

최근에는 연합형이 주류이며, 5장의 데이터 메시도 이 연합형 사고방식에 기반합니다.

4. 표준·프레임워크 - DAMA-DMBOK, DCAM, CDMC, DQC-V

네 가지는 경쟁 관계가 아니라 용도가 다른 도구입니다. DMBOK은 교과서, DCAM은 건강검진표, CDMC는 클라우드 안전점검표, DQC-V는 국가 품질 인증서에 가깝습니다. (요청하신 'DATA'는 DAMA-DMBOK으로 보고 정리했습니다.)

구분 만든 곳 성격 핵심 질문 이럴 때 쓴다
DAMA-DMBOK DAMA International 지식 체계(교과서) 데이터 관리에 무엇이 있나? 공통 용어 정리, 교육, 조직 설계
DCAM EDM Council 성숙도 평가 모델 우리는 몇 점인가? 현재 수준 진단, 로드맵 수립
CDMC EDM Council 클라우드 통제 프레임워크·인증 클라우드의 민감 데이터를 잘 통제하나? 클라우드·하이브리드 전환 시
DQC-V 한국데이터산업진흥원 (과기정통부) 국가 데이터 품질 인증 우리 데이터 자체의 오류율은? 대외 신뢰 확보, 데이터 거래

DAMA-DMBOK: 데이터 관리의 교과서

  • 11개 지식 영역 + 그 중심의 거버넌스 (1장 표 참고)
  • 성숙도 모델도, 규제도, 기술 매뉴얼도 아닌 참고 체계입니다(Snowflake)
  • 그래서 점수를 매기려면 DCAM 같은 평가 모델과 함께 씁니다

DCAM: 데이터 관리 역량 건강검진

  • 현재 버전은 v3.1이며, 8개 구성 영역의 세부 역량을 단계별 성숙도로 평가합니다(Snowflake)
  • 전략, 거버넌스, 품질, 운영, 분석까지 폭넓게 다룹니다
  • 금융권에서 출발해 규제 대응(예: BCBS 239)과 함께 많이 쓰입니다

CDMC: 클라우드 데이터 관리 체크리스트

  • 클라우드·멀티클라우드·하이브리드 환경의 민감 데이터 관리에 초점을 둔 프레임워크입니다
  • 6개 구성요소, 14개 역량, 37개 세부 역량으로 구성됩니다(Credly/EDM Council)
  • 특징은 자동화 가능한 핵심 통제: 소유자 등록, 자동 카탈로깅·분류, 접근 통제와 실시간 모니터링, 마스킹, 보존·폐기, Lineage 등(CDMC 통제 목록)
  • 오픈 라이선스로 공개되어 누구나 내부에서 활용할 수 있습니다(EDM Council)

DQC-V: 한국의 데이터 품질 인증

  • 한국데이터산업진흥원(K-DATA)이 운영하는 데이터 품질 인증으로, 기업·공공기관 시스템의 데이터 품질을 심사합니다(데일리안)
  • 등급은 플래티넘·골드·실버 3단계이며, 플래티넘은 데이터 정합률 약 99.97% 이상이 기준입니다(데일리안, 국민일보 쿠키뉴스)
  • 심사 항목 예: 데이터 표준, 업무 규칙, 패턴, 허용 범위, 코드값, 무결성
  • 「데이터 산업진흥 및 이용촉진에 관한 기본법」(2022년 시행)에 근거하며, 중소·초기 중견기업은 인증 비용을 지원받을 수 있습니다(뉴스서울, 2026년 지원사업 공고)
  • 같은 기관이 관리체계 인증(DQC-M), 보안 인증(DQC-S)도 운영합니다

실무 조합 예시: DMBOK으로 용어와 역할을 맞추고 → DCAM으로 현재 수준을 진단하고 → 클라우드 레이크하우스에는 CDMC 통제를 적용하고 → 핵심 시스템은 DQC-V로 품질을 대외 인증받습니다.

5. 데이터 메시(Data Mesh) 4원칙

데이터 메시는 중앙 데이터팀 한 곳이 모든 데이터를 처리하는 방식의 병목을 풀기 위한 조직·아키텍처 접근법입니다. 2019년 자막 데가니(Zhamak Dehghani)가 제안했으며, 도구 이름이 아니라 일하는 방식의 이름입니다.

원칙 한 줄 뜻 과거 방식과의 차이 거버넌스 관점에서 할 일
① 도메인 소유권 데이터를 만드는 업무팀이 책임진다 중앙 데이터팀이 전부 맡음 도메인별 Owner·Steward 지정
② 제품으로서의 데이터 데이터를 쓰는 사람이 고객이다 테이블만 던져두고 끝 설명서, 품질 SLA, 버전 관리
③ 셀프서비스 플랫폼 공통 도구로 각 팀이 스스로 만든다 요청서 넣고 몇 주 대기 표준 플랫폼과 템플릿 제공
④ 연합 계산 거버넌스 공통 규칙은 함께 정하고 자동 적용한다 수작업 검토·승인 정책을 코드화해 파이프라인에 내장

'데이터 제품'이 갖춰야 할 것

좋은 데이터 제품은 마트의 상품처럼 찾을 수 있고, 이해할 수 있고, 믿을 수 있고, 안전해야 합니다.

  • 찾기: 카탈로그에 등록되어 검색됨
  • 이해: 스키마, 용어 정의, 예시가 문서화됨
  • 신뢰: 품질 지표와 갱신 주기(SLA)가 공개됨
  • 안전: 접근 정책과 개인정보 등급이 붙어 있음
  • 연결: 다른 데이터 제품과 표준 키·형식으로 결합 가능

오해 바로잡기

  • 데이터 메시는 거버넌스를 없애는 것이 아닙니다. 오히려 거버넌스를 자동화해야 성립합니다.
  • 모든 조직에 맞지 않습니다. 도메인이 적고 데이터팀이 작다면 중앙형이 더 효율적일 수 있습니다.
  • 3장의 연합형 운영 모델이 데이터 메시의 조직적 바탕입니다.

6. 도구·플랫폼과 Iceberg/Polaris 연계

도구는 4기둥을 사람 대신 자동으로 지키게 해 주는 수단입니다. 규칙 없이 도구부터 사면 빈 카탈로그만 남습니다.

영역별 대표 도구

영역 오픈소스 상용·클라우드 역할
데이터 카탈로그·메타데이터 DataHub, OpenMetadata, Apache Atlas Collibra, Alation, Atlan 검색, 용어집, 소유자·분류 관리
테이블 카탈로그·접근통제 Apache Polaris, Unity Catalog OSS, Apache Ranger Databricks Unity Catalog, AWS Lake Formation, Snowflake Horizon 테이블 권한, 스토리지 키 관리
데이터 품질 Great Expectations, Soda Core, dbt tests Monte Carlo, Bigeye 규칙 검사, 이상 탐지
Lineage OpenLineage + Marquez, dbt docs Solidatus, Manta(IBM) 컬럼·테이블 계보 추적
개인정보 보호 Microsoft Presidio Immuta, Privacera 탐지, 마스킹, 가명처리

Iceberg와 Polaris는 거버넌스에서 무엇을 하나

  • Apache Iceberg는 객체 스토리지 위 파일을 테이블처럼 쓰게 해 주는 오픈 테이블 포맷입니다. 스냅샷과 스키마 변경 이력이 남아 "지난달 1일 기준 데이터"를 다시 조회(Time Travel)할 수 있고, 이는 감사와 재현성에 직접 쓰입니다.
  • 하지만 Iceberg 자체는 접근통제를 다루지 않습니다. 그 빈칸을 채우는 것이 카탈로그이고, Polaris가 그 역할을 합니다(DEV Community).
  • Apache Polaris는 Iceberg REST 카탈로그 스펙을 벤더 중립적으로 구현한 오픈소스 카탈로그로, Spark·Trino·Flink·Snowflake·Dremio 같은 여러 엔진이 같은 테이블을 바라보게 합니다. 2026년 2월 Apache 최상위 프로젝트(TLP)로 졸업했습니다(Apache Polaris 블로그).

엔진이 무엇이든 권한은 Polaris에서 한 번만 정의하고, 카탈로그·Lineage 도구는 옆에서 메타데이터와 실행 기록을 모읍니다.

Polaris의 두 가지 핵심 통제

1) 역할 기반 접근통제(RBAC): 권한은 카탈로그 역할에, 카탈로그 역할은 주체 역할에, 주체 역할은 사용자·서비스에 부여하는 단계식 구조입니다(Dremio). 메타데이터 조회 권한과 실제 데이터 읽기 권한(TABLE_READ_DATA)이 분리되어, "테이블 구조는 보되 내용은 못 보는" 설정이 가능합니다.

주체 역할 (사람·서비스 묶음) 부여할 카탈로그 역할 예시 가능한 일
data_engineer 생산 도메인 쓰기 역할 테이블 생성·적재
analyst 집계 스키마 읽기 역할 집계 테이블 조회만
ml_pipeline 학습용 데이터 읽기 역할 가명처리된 학습 데이터 읽기

2) Credential Vending(단기 자격증명 발급): 엔진에 영구 스토리지 키를 나눠 주지 않고, 질의할 때마다 권한 범위만큼의 짧은 수명 키를 발급합니다(Apache Polaris 문서). 키 유출 피해를 줄이고, "누가 어떤 파일을 읽었는지" 스토리지 감사 로그와 연결하기 쉽습니다.

연계 시 주의할 점

  • Polaris는 테이블 단위 접근제어가 강점이고, 비즈니스 용어집·도메인 소유자 같은 맥락 정보는 DataHub·OpenMetadata 같은 카탈로그와 함께 쓰는 편이 좋습니다.
  • 행·열 단위 마스킹은 엔진(Trino, Spark)이나 별도 정책 도구(Ranger 등)에서 처리하는 경우가 많으므로, 역할 이름과 분류 태그를 도구 간에 통일해야 합니다.
  • 폐쇄망에서도 Polaris는 Postgres 백엔드, Keycloak 인증, MinIO·Ozone·Ceph 스토리지와 조합해 자체 운영할 수 있습니다(Polaris 가이드).

7. 규제·법규와 AI 시대의 데이터 거버넌스

규제는 거버넌스를 하면 좋은 것에서 안 하면 위반인 것으로 바꿉니다. 2026년 기준으로 개인정보뿐 아니라 산업 데이터와 AI 학습 데이터까지 규제 범위가 넓어졌습니다.

주요 법규 한눈에 보기

제조 현장에서 특히 볼 것은 EU Data Act입니다. EU에 수출하는 설비나 센서가 만든 운영 데이터를 고객이 요청하면 제공해야 하므로, 어떤 데이터를 어떤 형식으로 갖고 있는지 메타데이터가 정리되어 있어야 대응할 수 있습니다.

규제가 거버넌스에 요구하는 공통 능력

  1. 데이터 지도: 어떤 데이터가 어디에 있고, 개인정보·민감정보인지 분류되어 있는가
  2. 목적과 근거: 왜 수집했고, 그 목적 안에서만 쓰는가
  3. 접근 통제와 감사 로그: 누가 봤는지 증명할 수 있는가
  4. 보존과 파기: 기한이 지난 데이터를 지우는가
  5. 추적성: 결과물(보고서, AI 모델)이 어떤 데이터에서 나왔는지 Lineage로 보여줄 수 있는가

AI 시대에 새로 생긴 거버넌스 과제

과제 왜 생겼나 대응 방법
학습 데이터 출처 관리 "이 모델 무슨 데이터로 학습했나"를 규제가 묻기 시작 데이터셋 버전 고정(Iceberg 스냅샷), 데이터 카드 작성
품질·편향 점검 나쁜 데이터는 나쁜 모델을 그대로 만든다 학습 전 품질 규칙 검사, 집단별 분포 점검
비정형 데이터 관리 문서·이미지·로그가 RAG와 학습에 대량 투입 문서에도 소유자·민감도 태그, 카탈로그 등록
RAG 권한 상속 원문서 권한이 벡터 DB에서 사라지는 문제 검색 시점에 원문서 접근권한을 다시 확인
모델·프롬프트 Lineage 데이터 → 피처 → 모델 → 예측까지 추적 필요 모델 레지스트리와 OpenLineage 연동
AI가 데이터를 직접 조회 AI 에이전트가 카탈로그·DB에 직접 접근 사람과 같은 RBAC 적용, 에이전트 전용 주체 역할

정리하면, AI 거버넌스는 데이터 거버넌스 위에 세워집니다. 데이터의 품질, 출처, 권한이 관리되지 않으면 AI 모델에 대해서도 아무것도 설명할 수 없습니다.

8. 도입 단계와 실패 안티패턴

성공하는 도입의 공통점은 전사를 한 번에 바꾸려 하지 않고, 아픈 문제 하나를 골라 작게 증명한 뒤 넓히는 것입니다. 단계별 기간은 조직 규모에 따라 다릅니다.

파일럿(3단계)이 가장 중요합니다. 여기서 "에너지 대시보드 오류 문의가 줄었다"처럼 숫자로 보여줄 성과가 나오지 않으면 확산 단계의 예산과 협조를 얻기 어렵습니다.

단계별 체크리스트

  • 거버넌스로 해결할 업무 문제를 한 문장으로 정의했다
  • 경영진 스폰서(CDO 또는 담당 임원)가 있다
  • 파일럿 도메인의 Owner와 Steward가 이름으로 지정되었다
  • 핵심 데이터 요소(CDE) 10~20개의 정의와 품질 규칙을 만들었다
  • 품질 점수·카탈로그 등록률 같은 측정 지표를 정했다
  • 규칙을 파이프라인·카탈로그에 자동으로 적용했다

자주 보는 실패 안티패턴

안티패턴 증상 처방
도구부터 사기 비싼 카탈로그를 샀는데 아무도 등록·검색하지 않음 문제·역할·규칙 먼저, 도구는 나중에
문서만 있는 거버넌스 두꺼운 정책서는 있지만 실제 시스템과 연결되지 않음 정책을 코드·파이프라인 검사로 자동화
빅뱅(Big Bang) 전사 모든 테이블을 한 번에 정리하려다 지침 핵심 데이터 요소부터, 도메인 하나부터
IT 혼자 추진 현업은 "IT 일"로 여기고 참여하지 않음 Owner는 현업 부서장, IT는 Custodian

성과 측정 없음 "좋아진 것 같은데" 수준에서 예산 삭감 품질 점수, 오류 문의 건수, 데이터 찾는 시간 추적
한 번 하고 끝 프로젝트 종료 후 카탈로그가 다시 낡아감 거버넌스를 프로젝트가 아닌 상시 운영 업무로
메시 흉내내기 도메인에 책임만 넘기고 플랫폼·공통 규칙은 없음 셀프서비스 플랫폼과 연합 규칙을 먼저 준비
