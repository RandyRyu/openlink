03

시스템 아키텍처 가이드 핵심

30개 섹션 · 설계 종합 레퍼런스

원칙 1 — 인프라 SSoT

모든 파이프라인 설정의 원본은 DF-Stream DB에 있다. Benthos·Kafka·SR·KEPServer는 DB 내용을 반영한 결과물. DFSTREAM-336 이후 KEP 노드도 예외 없이 편입.

원칙 2 — 의미론 SSoT

모든 데이터의 정의·명칭 원본은 표준 사전(data_standard)에 있다. 새 코드 테이블(_ct) DDL 생성 금지 → 사전 카테고리 추가. 태그 자유 텍스트 분류 금지.

데이터 카탈로그 — 자동화 4계층 신규

── 1) Listener · 즉시 ─────────────────── 스트림 deploy/redeploy/start 이벤트 ↓ ensureDataset dataset row + lineage edge 즉시 등록 ── 2) Backfill cron · 1시간 ────────────── 전 dataset 의 누락·불완전 lineage 보강 listener 미완 row 재발급 ── 3) Freshness cron · 1분 ─────────────── sink 의 MAX(audit ts) → last_ingest_at sink DB readonly 별도 connection ── 4) UI 표시 ──────────────────────────── 검색 / 상세 / lineage chain / 미리보기 / 쿼리
주요 테이블 : catalog_dataset_mt · catalog_dataset_column_jt · data_lineage_jt · catalog_query_history_jt (모두 df_app)

카탈로그 거버넌스 — 사업장 격리 신규

── 조회 스코핑 (692) ───────────────────── read 토큰(df-port) 의 businessPlaceUids ↓ 서버측 스코핑 범위 밖 데이터셋 → 404 (fail-closed) ── SQL 콘솔 격리 (706) ─────────────────── 진입 데이터셋 schema 별 ↓ SET LOCAL ROLE catalog_reader_<schema> 타 사업장 schema 참조 → PG 42501 물리 차단 ── 사용처 리댁션 (705) ─────────────────── 제목·딥링크 : admin / developer / 소유자 그 외 뷰어 : 개수·종류만 노출

BI 데이터 탐색 — df-port 연동 신규

저장은 구성(config)만 · 데이터 복사 없음 (zero-copy) 게이트웨이 (df-port) │ config → 안전 SQL 골격 조립 │ 값은 스칼라 params ($1..) 로 분리 ↓ 실행·물리 강제 (df-stream runQuery) 사업장 격리 : SET LOCAL ROLE catalog_reader_* SELECT-only : readonly role (DDL/DML PG 거부) 파라미터 바인딩: $1 서버측 · IN($1,$2) 전개 타임존 : tz 기본 Asia/Seoul 자원 상한 : 자동 LIMIT + statement_timeout 5s 기능 : 차원 · 측정값(count/sum/avg/min/max/stddev) · 다차원 GROUP BY · 시간버킷 조인 → 7종 차트

태그 상태 — 실측 유입 기준 재정의 신규

최근 5분 창의 폴링 유입 건수로 판정. 구독(subscribe)은 값 변화 시에만 유입되어 오탐을 유발하므로 제외.
🟢 정상 ≥ 3건 — 데이터가 최신으로 흐름
🟡 지연 1~2건 — 유입은 있으나 주기보다 느림
🔴 끊김 0건 — 최근 5분 유입 없음, 장애 의심
⚪ unknown 캐시 콜드스타트 — 초록 오인 방지
TagIngestCache 30초 주기 갱신 · 목록 hot-path O(1) 조회. 정의 불일치(drift)는 태그 상세에서 별도 확인.

TimescaleDB 표준 정책 (DFSTREAM-540)

신규 공장 생성 시 자동 적용 │ TagRtProvisionService ↓ chunk_time_interval : 6 hours compress_segmentby : opc_server_node_nm compress_orderby : opc_server_dtm DESC 압축 정책 : 3 hours retention 정책 : 30 days CAGG mv_tag_rt_5m : 5분 refresh └ CAGG 자체도 압축 3h · retention 30d 실측 절감 894MB → 46MB (~95%)

Tag Lifecycle (DFSTREAM-485)

DRAFT 노드 정보 입력 + KEP push
PENDING_PUSH transient — KEP push 대기
ACTIVE 표준화 완료 → 카탈로그 반영
DEPRECATED PLC 주소 변경 — lineage 보존
2-step Wizard(노드 5필드 → 표준화 표) · PLC 값 라이브 미리보기(previewToken) · OPC Driver Matrix.

1:1:1:1 정책 — 공장 단위 격리

공장 : changwon_srl Stream : changwon-srl-kepserver1-01 Topic : css.changwon_srl.tag Connector : css.changwon_srl.tag.sink DB Table : changwon_srl.tag_rt 한 공장 장애가 다른 공장에 영향 없음. 독립 운영 · 장애 추적 · 스키마 분리 보장.

정합성·자가치유 계층 — 4축 + 3단계 신뢰 모델

"장부(DB) vs 실제 선반(런타임)" 을 주기 대조 — 창고 재고 실사 방식 DB = SSoT benthos_pipeline_mt · tag_mt · connector · device_mt │ ├─ ① Benthos 스트림 런타임 reconcile cron ├─ ② KEPServer 태그 kep-drift-sync ├─ ③ Kafka Connect sink dead-sink 자동회복 └─ ④ device 공장 정합 안전망 cron (매시간 recompute) ↓ 불일치 → 인앱 알림 + SigNoz ───── 신뢰 단계 (위험도별 차등 적용) ───────────────── Phase 1 — 감지 + 알림 : cron 이 drift 기록·알림, 수정 안 함(read-only) N회 연속 확정(flapping 방지) · 인스턴스 장애 skip Phase 2 — 수동 승인 복구 : 운영자가 화면에서 확인 후 버튼으로 재배포/중지 Phase 3 — 자동 복구 : dry-run 검증 후 활성화 예정 (DFSTREAM-617)
