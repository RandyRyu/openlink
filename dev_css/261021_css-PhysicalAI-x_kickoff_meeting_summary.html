결론 ②데이터 접근은 “DataForge 우선, 안 되면 로우 데이터”

회의 5

DataForge에 정리된 데이터 품질이 예상보다 좋아, 우선 DataForge 데이터로 접근하고 부족할 때만 레벨2 로우 데이터로 내려가기로 했습니다. 1차 연도 목표(표준화·수집)는 DataForge 기준으로 달성 가능하다고 판단됐습니다.

결론 ③없는 데이터로 시작하지 않는다

회의 5

수행사가 명확히 했습니다 — 기존 데이터 기반으로만 진행하며, 2~3차 연도에 센서를 대거 추가하는 방향은 고려하지 않습니다. 다만 세아 측은 품질 예측에 정말 크리티컬한 수작업 데이터가 있다면 그 부분은 추가 수집을 검토해야 한다는 의견을 냈습니다.

결론 ④남은 결정 사항

회의 5
  • 우선순위 딜레마 — 수행사는 기존 모델이 있어 빨리 할 수 있는 전기로를 먼저, 세아 내부 우선순위는 다른 쪽. “빨리 할 수 있는 것 vs 더 중요한 것”을 함께 결정해야 함
  • DataForge 팀의 분석 지원 역할 — 분석 용역이 아니라 현업과의 중간 소통 창구 역할. 언제(2년차? 3년차?) 어느 수준으로 필요한지 세아 내부 결정 필요
  • DataForge 클라우드 사용 비용 — 용역 예산이 아니라 세아창원이 결정. 서비스 계정별로 비용 추적 가능

다섯 번의 회의를 관통하는 쟁점

쟁점 1유스케이스를 먼저 확정하지 않으면 과제가 실패한다

이 미팅 전체를 관통하는 가장 강한 메시지였습니다. 데이터 수집 자체는 문제가 아니라는 것이 VNTG 측 입장입니다. L0~L3 데이터는 대부분 보유하고 있고 수집 체계도 갖춰져 있습니다.

문제는 “과제가 필요로 하는 바로 그 데이터가 실제로 존재하느냐”이고, 그것은 유스케이스가 정해져야만 판단할 수 있습니다. 유스케이스를 잘못 잡으면 수집 불가능한 데이터를 전제로 한 과제가 되어버립니다.

판단 순서 ───────────────────────────── ① 유스케이스(과제 포인트) 확정 │ ↓ ② 유스케이스별 필요 데이터 정의 │ ↓ ③ 해당 데이터가 그 공장에 실제로 있는지 확인 │ ↓ ④ 없으면 — 신규 수집? 대체? 범위 재조정
→ 회의 5에서 유스케이스 1차안이 나왔고, 수행사가 유스케이스별 데이터 리스트를 만들어 VNTG와 수집 가능 여부를 검토하는 절차로 정리됨.

쟁점 2설비 노후화와 차세대 재구축의 충돌

대상 3개 공장은 설비가 노후해 레벨2 시스템 재구축이 논의 중인 상태입니다. 30년 이상 된 PLC·장치가 붙어 있어 신호 유실이 발생하고, DataForge 쪽에서 보정 로직을 다수 넣어 운영하고 있습니다.

여기서 “없는 데이터를 새로 수집하자”는 요구가 나오면 재구축 범위와 얽혀 비용이 늘고, 다시 축소되는 악순환에 빠질 수 있다는 우려가 제기됐습니다.

쟁점 3데이터 외부 제공 — 가장 충돌이 컸던 지점

과제 산출물로 요구되는 1,600TB 공공 데이터 제공용량 확인 필요에 대해 세아 측이 강하게 반발했습니다.

  • 마스킹·비식별화 후 제공하면 그만큼의 양이 나오지 않을 것
  • 경남 데이터센터 클라우드에 누가 접속하고 누가 관리·책임지는지가 전혀 정의되어 있지 않음
  • 타 사업 경험상 과업과 무관한 설비 데이터만 쌓이는 패턴이 반복됨
“공공 활용이 목적이라면 세아에 요청하고 승인받고, 누가 어떻게 쓰고 관리할지 명확히 한 뒤에야 논의 가능하다. 동의한 바가 없다.”
→ 회의 5에서 정리: 타 총괄이 실제 과업을 수행해야 하면 반출 없이 세아 내부에서 함께 작업하고, 과업상 약속된 반출분만 마스킹해 제공. 공유 형식·마스킹 수준은 별도 협의하며 전달 전 세아 검토 필수.

쟁점 4현업 수용성 — 기술보다 어려운 문제

회의 4에서 나온 이야기입니다. 시스템을 잘 만들어도 현장이 쓰지 않으면 버려집니다. 이상 알림에 라벨을 선택해줘야 학습이 되는 구조인데 그 선택조차 하지 않으려 합니다.

“내가 열심히 해서 품질이 좋아지면 나한테 무슨 이득이 있나?” — 현업에게 돌아가는 이익을 설계하지 못하면 AX는 실패한다.
