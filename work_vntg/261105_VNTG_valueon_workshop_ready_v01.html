1워크샵 기본 틀과 조직장 작성안 관찰

핵심가치 정의는 토의 시트 순서입니다.

가치작성안 번호정의
🚀 혁신1번문제를 새롭게 정의하고 경험과 기술을 연결해 창조적으로 도전하고 실현한다.
🌱 배려5번상대방의 의견을 경청하고 공감하며 존중한다.
🤝 신뢰3번진정성 있게 소통하고 전문성으로 답하고 실행력으로 보여준다.
🎯 책임2번문제의 본질을 직시하고 주도적으로 해결한다.
☀️ 긍정4번밝은 에너지로 서로의 시도를 응원한다.

진행 규칙

  • 가치당 5분, 모든 조가 5개 가치를 모두 이야기합니다.
  • 합의할 필요는 없습니다. 조마다 다른 의견이 나와도 그대로 공유합니다.
  • 이전 조와 같은 의견은 “○조와 같습니다”로 넘어갑니다.
  • 작성안 문장은 ‘닉네임+번호’로 부릅니다. 번호는 가치 번호입니다(혁신 1 · 책임 2 · 신뢰 3 · 긍정 4 · 배려 5). 예: 랜디님 1번.
  • 토의 후 구글폼(forms.gle/dSjfX7dFFBFm7FJF8)에 후기·이견·추가 의견을 남깁니다.

조직장 작성안에서 보이는 것

  • 세 분이 공통으로 쓴 것 — 반복 업무 자동화(혁신), 임시 조치가 아닌 근본 원인 해결(책임), 근거·로그를 남기는 소통(신뢰), 상대 눈높이에 맞춘 설명(배려). 이 네 가지는 ‘이미 합의된 기본’으로 보고 빠르게 넘어가도 됩니다.
  • 세 분의 시선 차이 — 테디님은 협업 태도(솔직한 공유, 경청, 감사), 랜디님은 시스템 안정성(아키텍처, 보안, 모니터링, 스테이징), 찬희님은 개발 실무(코드 근거, 리뷰, 운영 고려)에 무게가 있습니다. 조 토의에서는 ‘우리 파트는 어느 쪽에 가까운가’를 물으면 이야기가 잘 열립니다.
  • 상대적으로 덜 다뤄진 것 — 배려는 찬희님이 1문장만 썼고, ‘거절·우선순위 조정’처럼 요청을 다 받아줄 수 없을 때의 배려는 아무도 다루지 않았습니다. 긍정은 장애·요청 대응이 많은 우리 업무 특성과 부딪힐 수 있는 지점이라 이견이 나올 가능성이 큽니다.

2조별 토의 시트 작성안

토의 시트의 칸 구성에 맞춰 채운 예시입니다. 조 토의의 출발점으로 쓰고, 조 의견으로 바꿔 적어 주세요.

핵심가치① 우리 센터에서 잘 작동할까요? (이유·상황)② 다른 의견 · 추가하고 싶은 것발표용 한 줄
🚀 혁신문제를 새롭게 정의하고 경험과 기술을 연결해 창조적으로 도전하고 실현한다.
☑ 그대로 잘 작동할 것 같아요☐ 어려운 부분이 있어요(단, 개선 시간이 확보된다는 전제)
잘 작동하는 이유·상황
  • 반복 업무 자동화는 이미 우리 일상입니다. WG 태그 등록(요청 분석→KEPServerEX 확인→표준화→Web Gateway 등록→NiFi·Kafka·DB 설정)처럼 절차가 정해진 일이 많아 자동화 대상이 분명합니다.
  • AI 에이전트로 랜딩페이지 서버 긴급 교체를 무중단으로 끝낸 사례, 수집 이상 감지 알람 프롬프트 작업처럼 새 도구를 실제 업무에 붙이고 있습니다.
어려운 부분
  • WG 요청을 우선 처리하느라 개선 과제(Cloud Run·GCS 커넥션 개선, 소재 ID 매칭 비용 최적화)가 반복해서 홀딩됩니다. 혁신할 시간이 구조적으로 부족합니다.
  • ‘신중하게 도입한다’(테디님·찬희님 1번)가 ‘그래서 안 한다’의 이유가 되지 않도록 검토 기준이 필요합니다.
  • 혁신의 출발점은 ‘문제 재정의’입니다. 같은 요청이 세 번 반복되면 처리 속도를 올리는 대신 요청 자체를 없애는 셀프서비스(DF-Stream 메타데이터 기반 등록)로 바꾸자는 의견.
  • 운영 요청과 분리된 개선·실험 시간(예: 주 1회 반나절, 분기별 개선 과제 1건)을 팀 규칙으로 두자.
  • 실험 결과가 ‘안 된다’여도 Confluence에 남기기. GCS 외부테이블 + 예약쿼리 대체 테스트처럼 실패도 자산입니다.
“반복 요청은 빨리 처리하는 것보다 없애는 것이 혁신이다 — 자동화·셀프서비스로 바꾸되, 실험할 시간은 따로 떼어 두자.”
🌱 배려상대방의 의견을 경청하고 공감하며 존중한다.
☐ 그대로 잘 작동할 것 같아요☑ 어려운 부분이 있어요(고객·현업 요청이 많은 구조라 기준이 필요)
잘 작동하는 이유·상황
  • 우리 고객은 제강·압연·환경·스마트팩토리팀 같은 현업이라 기술 용어를 매번 풀어서 설명해야 합니다. 랜디님·찬희님 5번(상대 관점의 언어, 눈높이 설명)은 바로 쓰이는 문장입니다.
  • 그라파나 사용자 교육, 분리된 스테이징 환경 유지처럼 상대의 부담을 덜어주는 일을 이미 하고 있습니다.
어려운 부분
  • 배려가 ‘요청을 다 들어주기’로 오해되면 팀이 감당할 수 없습니다. DataForge 설계 방향 문서의 ‘하고 싶어도 하지 말아야 하는 것’(설비 제어, 분석·모델링 등)과 부딪힙니다.
  • 인프라·수집·개발·기획 파트끼리 서로의 업무 상황을 잘 몰라 의도치 않게 부담을 주는 경우가 있습니다.
  • ‘안 되는 것은 이유와 대안을 함께 말하는 정중한 거절’도 배려에 포함하자.
  • 다음 담당자를 위한 문서·인수인계도 배려입니다(테디님 2번 ‘다음 담당자까지 고려’와 연결).
  • 배려 대상에 야간·휴일 알람을 받는 동료도 넣자 — 불필요한 알람 줄이기.
“상대의 언어로 설명하고, 안 되는 것은 이유와 대안을 함께 말하는 것까지가 배려다.”
🤝 신뢰진정성 있게 소통하고 전문성으로 답하고 실행력으로 보여준다.
☑ 그대로 잘 작동할 것 같아요☐ 어려운 부분이 있어요(이미 문화로 자리 잡은 부분이 많음)
잘 작동하는 이유·상황
  • Task 페이지 템플릿(Page Owner, 수행 History), 장애 분석 문서(Pgpool-II 비정상 종료, InfluxDB 재시작, PK 중복 오류)가 로그·지표 기반으로 쓰이고 있어 랜디님·찬희님 3번과 그대로 맞습니다.
  • 보안 취약점(PHP) 공개 후 며칠 안에 Zabbix·랜딩페이지 조치를 끝내고 결과를 공유한 것처럼, 실행으로 보여주는 경험이 쌓여 있습니다.
어려운 부분
  • 고객 일정에 묶인 일(PLC 재부팅은 비조업일만 가능, 고객 회신 대기)은 지연을 숨기지는 않지만 ‘늦게’ 공유되기 쉽습니다.
  • 문서는 많은데 찾기 어려우면 신뢰의 근거가 되지 못합니다.
  • ‘지연이 확실해졌을 때’가 아니라 ‘지연 가능성이 보일 때’ 먼저 말하는 것을 기준으로 삼자.
  • 문서는 쓰는 것에서 끝나지 않고 찾을 수 있어야 합니다(제목 규칙, 상위 페이지 정리, 링크).
  • 장애 회고는 사람이 아니라 원인과 장치를 다룬다는 원칙(blameless)을 명문화하자.
“근거를 남기고, 늦어질 것 같으면 먼저 말한다 — 기록과 선(先)공유가 신뢰를 만든다.”
🎯 책임문제의 본질을 직시하고 주도적으로 해결한다.
☑ 그대로 잘 작동할 것 같아요☐ 어려운 부분이 있어요(단, ‘우리 범위 밖’ 원인에 대한 기준 보완)
잘 작동하는 이유·상황
  • 세 분 모두 ‘임시 조치가 아닌 근본 원인’을 썼고, 실제로도 Grafana 쿼리 → Pgpool 에러, measurement 정규식 쿼리 → InfluxDB 재시작처럼 원인까지 추적해 고치고 있습니다.
  • MES 수집 데이터 변경 이력 정책처럼 단건 요청을 공통 정책·매뉴얼로 만들어 재발을 막는 사례가 있습니다.
어려운 부분
  • 원인이 고객 설비·네트워크·타 시스템(L2, MES)일 때 우리가 어디까지 ‘주도’해야 하는지 경계가 모호합니다. 그런 건은 HOLD로 길어집니다.
  • 의지와 상관없이 주어지는 과제(용역 계약 등)에서는 주도성을 유지하기 어렵고, 근본 원인 분석은 시간이 드는데 성과로 잘 보이지 않습니다.
  • 우리 범위 밖이면 ‘고칠 사람을 찾아 끝까지 연결하고 다시 확인하는 것’까지가 책임이라고 정의하자.
  • 재발 방지는 문서가 아니라 장치(알람, 체크리스트, 테스트)로 남기자.
  • 근본 원인 해결 같은 보이지 않는 성과도 평가에 반영되었으면 한다.
“고칠 수 없으면 고칠 사람에게 끝까지 연결한다 — 그리고 재발 방지는 장치로 남긴다.”
☀️ 긍정밝은 에너지로 서로의 시도를 응원한다.
☐ 그대로 잘 작동할 것 같아요☑ 어려운 부분이 있어요(장애·요청 대응 중심 업무와의 긴장)
잘 작동하는 이유·상황
  • 찬희님 4번(사람보다 문제에 집중), 랜디님 4번(작은 기술 성과를 적극 공유)은 오늘부터 바로 실천할 수 있는 문장입니다.
  • DF-Stream·DF-Port 패키지, 데이터 에이전트(NL2SQL) PoC처럼 새로운 시도가 실제로 진행되고 있습니다.
어려운 부분
  • 업무 대부분이 장애·요청 대응이라 ‘문제’만 보이는 구조입니다. 오래된 시스템(예: InfluxDB 1.8, 지원 종료된 서버)이 주는 부담도 큽니다.
  • 새 시도가 길어지면 응원보다 ‘언제 끝나요?’가 먼저 나오기 쉽습니다.
  • 긍정을 ‘무조건 낙관’이 아니라 ‘안 된다 대신 어떻게 하면으로 시작하는 태도’로 정의하자.
  • 주간회의에 ‘이번 주 잘된 것 1개’ 칸을 두는 등 작은 성과를 나누는 루틴을 만들자.
  • 실험이 실패해도 수고와 배운 점을 인정하자.
“작은 성공을 자주 나누고, 어려운 문제는 ‘안 된다’ 대신 ‘어떻게 하면’으로 시작한다.”

  • 팀 운영(공수·비용·출장·휴가), 계약·청구(매월 25일 전월 실적 청구)
  • DataForge 라이선스 체계 재설계, DF 정책·표준(Naming Rule, 용어 정의)
  • 신규 기안(MLOps, 보안 비식별화 엔진, 양방향 안전 인터락, ISA-95·OPC-UA·AAS 적용)
  • 고객 협의(GCP 데이터 보관기간 등), 대외 과제(탄소발자국 국책과제, 경남 피지컬 AI 용역)

🚀 혁신

  • 테디님 1번 ‘재사용성과 확장성을 검토해 신중하게 도입’, 찬희님 1번 ‘필요한지 검토·실험 후 적용’에 공감할 것입니다.
  • “기안은 계속 나오는데 실행할 사람과 시간이 없다. 쌓이는 기안도 피로다.”
  • 고객 요구가 수집 → 분석 → AI 중심으로 빠르게 바뀌어 방향을 다시 잡는 비용이 큽니다.
  • 기안 단계에서 ‘하지 않을 것’도 함께 정하기(설계 방향 문서의 ‘하지 말아야 하는 것’처럼).
  • 기안 → PoC → 적용 단계마다 계속/중단을 판단하는 게이트 두기.

🌱 배려

  • 테디님 5번 ‘규정과 기한이 정해진 업무는 서로의 일정을 존중하고 예외 요청을 최소화’ — 청구·공수·출장 보고를 챙기는 입장에서 가장 와닿는 문장.
  • 고객 창구 역할이라 고객과 팀원 사이에서 ‘양쪽을 배려’하다 충돌이 생깁니다.
  • 팀의 의지와 상관없이 들어오는 과제를 받을 때 팀원 부담을 어떻게 배려할지 고민.
  • 요청 접수 시 ‘수용 / 조건부 수용 / 거절’ 기준을 팀에 공유.
  • 업무를 배분할 때 이유와 배경을 함께 설명하기.

🤝 신뢰

  • 테디님 3번 ‘좋은 소식과 어려운 점 모두를 솔직하고 투명하게 공유’.
  • 라이선스·청구는 숫자의 근거가 곧 신뢰입니다. 운영 공수가 섞여 과다청구로 보였던 AS-IS 이슈를 겪었습니다.
  • 고객에게 말한 내용과 팀 내부 이해가 다르면 신뢰가 깨집니다.
  • 공수·비용·사용량은 실측 근거로 말하기.
  • 고객 협의 결과는 주간회의를 기다리지 말고 바로 팀에 공유.

🎯 책임

  • 테디님 2번 ‘다음 업무와 다음 담당자까지 고려하여 연결성을 갖고 수행’.
  • 사업총괄·DataForge·DX서비스팀 사이에서 누가 결정하는지 모호한 과제가 있습니다(예: 대외 과제 수행 여부는 사업총괄-DF 합의로 판단).
  • 팀 R&R의 Main/Sub/Pair 구조를 과제 단위로도 적용하고, 의사결정 주체를 문서 첫머리에 명시.

☀️ 긍정

  • 테디님 4번 ‘어려운 상황에서도 서로에게 감사’.
  • 정책·라이선스 같은 장기 과제는 성과가 늦게 보여 지치기 쉽습니다.
  • 마일스톤 단위로 작은 완료를 축하.
  • 주간회의·워크샵에 동료 칭찬 코너.
🖥️

인프라 파트

주요 업무
  • Edge 서버(HyperFlex, VM) 구축·운영, 정기 점검, 도메인·인증서
  • Cloud(GCP·AWS) 구축·운영, VPC·네트워크 연결
  • 관제(Zabbix, Intersight), 백업 관리(Bacula·Duplicati)
  • DBA(PostgreSQL·BigQuery 설계·튜닝·계정 권한), 보안 취약점 대응

🚀 혁신

  • 랜디님 1번 ‘휴먼 에러를 원천 차단하는 아키텍처’, ‘회복 탄력성을 높이는 방어 로직’.
  • “안정성이 최우선이다. 검증 안 된 신기술은 운영에 바로 넣으면 안 된다.”
  • 폐쇄망·고객사 IDC·보안 정책 때문에 새 도구 도입 장벽이 높습니다.
  • 새 기술은 테스트 환경에서 먼저 검증한다는 원칙.
  • 혁신의 첫 대상은 점검·백업·알람 분석 자동화(Zabbix 느린 쿼리 AI 분석 등).

🌱 배려

  • 랜디님 5번 ‘분리된 스테이징 환경을 꼼꼼하게 유지보수해 심리적 부담을 덜어준다’.
  • 디스크 교체, 버전 업그레이드 같은 작업은 다른 파트와 고객에 영향을 주는데 사전 공지가 부족하면 불만이 생깁니다.
  • 야간·휴일 알람 대응 부담.
  • 작업 공지 템플릿(일시·영향 범위·롤백 방법) 사용.
  • 알람 노이즈를 줄이는 것도 동료에 대한 배려로 보기.

🤝 신뢰

  • 랜디님 3번 ‘책임 추궁보다 객관적인 로그와 지표를 공유하며 문제 해결에 집중’.
  • 원인이 쿼리·애플리케이션 쪽인데 ‘인프라 문제’로 먼저 의심받는 경우가 있습니다(InfluxDB 재시작의 실제 원인은 정규식 쿼리).
  • 파트 공통 관측 대시보드에서 같은 데이터를 보고 이야기하기.

🎯 책임

  • 랜디님 2번 ‘개발 초기부터 보안 요건을 핵심 과제로’, ‘모니터링 및 알람 환경을 사전에 준비’.
  • 소수 인원이 Edge·Cloud·DB·보안을 모두 맡아 ‘주도적으로 다’ 하기엔 한계가 있습니다.
  • 고객 IT·생산 시스템 팀의 권한이 있어야 끝낼 수 있는 일이 많습니다.
  • 책임 범위와 대응 수준(SLA)을 문서로 명확히.
  • 운영 지식을 Runbook으로 만들어 한 사람에게 쏠리는 의존도 낮추기.

☀️ 긍정

  • 랜디님 4번 ‘레거시를 불평하기보다 점진적 리팩토링으로 성장의 기회로’.
  • 잘 돌아가면 아무도 모르고 장애 때만 주목받습니다. 인정받기 어려운 일.
  • ‘장애 0건 주간’, 취약점 선제 대응도 성과로 공유하고 칭찬하기.
🔌

수집·운영 파트

주요 업무
  • Tag·Legacy 수집 파이프라인 구축·운영(KEPServerEX → NiFi → Kafka → PostgreSQL·InfluxDB·BigQuery)
  • WG 요청·문의 처리(태그 등록, No Data 원인 확인, MES 데이터 추가)
  • 소재 ID 트래킹, DW·데이터 마트, 외부 전송(FEMS, 국책과제)
  • 수집 모니터링·이상 감지, 그라파나 사용자 교육

🚀 혁신

  • 테디님·찬희님 1번 ‘반복 업무를 적극적으로 자동화’ — 태그 등록 절차가 가장 대표적인 자동화 대상이라는 데 강하게 공감.
  • “WG 요청 우선 처리로 개선 과제가 계속 홀딩된다.” 주간회의 기록에 실제로 반복되는 문구입니다.
  • 태그 등록 자동화·셀프서비스를 실 차원의 1순위 개선 과제로.
  • 개선 과제는 요청 처리와 분리된 보호 시간에 진행.

🌱 배려

  • 찬희님 5번 ‘협업하는 구성원의 제약사항을 이해하고 눈높이에 맞게 설명’.
  • 태그 설명·목적을 받지 못하거나 회신이 늦어 일정이 밀립니다. 배려가 일방향이라는 느낌.
  • ‘No Data’ 문의는 원인이 설비·네트워크·쿼리 등 다양해 설명이 길어집니다.
  • 요청 양식에 필수 정보(태그 설명, 사용 목적, 희망 일정)를 넣어 서로의 수고 줄이기.
  • 자주 묻는 문의는 가이드 문서로.

🤝 신뢰

  • 찬희님 3번 ‘일정 지연, 기술적 어려움, 예상되는 위험은 숨기지 않고 빠르게 공유’.
  • 데이터 누락을 고객이 먼저 발견하면 신뢰가 크게 떨어집니다.
  • 수집 이상 감지·알람을 고도화해 ‘우리가 먼저 알고 먼저 알리기’.
  • 요청 처리 결과를 회신하는 기준(언제·무엇을) 맞추기.

🎯 책임

  • 테디님·찬희님 2번 ‘임시 조치에 그치지 않고 원인을 찾아 반복되지 않게’ — Cloud Run SSLEOFError, PK 중복 오류 대응 경험.
  • 원인이 고객 설비 쪽(PLC 재부팅은 비조업일만 가능 등)이라 우리가 끝낼 수 없는 건이 HOLD로 길어집니다.
  • HOLD 건마다 소유자와 재확인 날짜를 명시.

☀️ 긍정

  • 찬희님 4번 ‘익숙하지 않은 기술도 피하기보다 배우고 해결할 방법을 먼저 찾는다’.
  • 반복 요청에 지치기 쉽습니다. “또 태그 등록이야?”
  • 수집한 데이터가 어떤 대시보드·분석·과제에 쓰였는지 공유해 일의 의미를 보이기.
  • 고객의 감사 피드백을 팀에 전달.
🛠️

서비스 개발 파트

주요 업무
  • Web Gateway 운영·개발(요청·문의 관리, Frontend·Backend)
  • DF-Stream(운영자용)·DF-Port(사용자용) 패키지 모노레포 개발, OIDC 통합 인증
  • GKE 배포, VM 서비스의 Cloud Run 전환, 가시화 도구(Grafana·Metabase) 구현
  • Grafana TimescaleDB 플러그인, 태그 표준화(ISA-95 설비 카탈로그)

🚀 혁신

  • 찬희님 1번 ‘문제 해결에 필요한지 충분히 검토하고 실험한 후 적용’, 랜디님 1번 ‘아키텍처를 선제적으로 설계’.
  • 실험이 길어지면 운영·고객 요청과 충돌합니다(TimescaleDB 플러그인 HOLD).
  • 설계 원칙 ‘Simple is Best’와 새 기술을 써보고 싶은 마음 사이의 긴장.
  • 기술 선정 기준표(재사용성·운영 부담·비용·대체 가능성)를 실 공통으로.
  • AI 코딩·에이전트 도구 사용 경험과 가이드를 공유.

🌱 배려

  • 찬희님 5번 ‘기획·디자인·운영 등 협업하는 구성원의 의견과 제약사항을 이해’.
  • 실제 사용자(운영 담당자, 현업)의 목소리를 개발자가 직접 듣기 어렵습니다.
  • QA 요청을 보내도 피드백이 적습니다.
  • QA 시트·버그 리포트 창구에 응답하는 문화를 실 전체로.
  • 짧은 사용자 인터뷰·현장 관찰 기회 만들기.

🤝 신뢰

  • 찬희님 3번 ‘코드와 기술적 의사결정에 이유와 근거를 남긴다’, 랜디님 3번 ‘문서 작성을 일상화’.
  • 패키지 개발처럼 긴 일정은 테스트·출시 지연을 언제 알릴지 애매합니다.
  • 아키텍처 결정 기록(ADR) 도입.
  • 정기 데모로 진행 상황을 ‘실행력으로 보여주기’.

🎯 책임

  • 찬희님 2번 ‘운영과 유지보수까지 고려한 구조’, 랜디님 2번 ‘개발 초기부터 보안 요건’.
  • 만든 사람이 운영까지 맡으면 신규 개발 속도가 떨어집니다.
  • 배포 전 체크리스트(모니터링·알람·롤백·문서)를 ‘완료의 정의’에 포함.

☀️ 긍정

  • 랜디님 4번 ‘가볍고 작은 기능을 통한 기술적 성과를 적극 공유’.
  • 장기 패키지 개발은 완성 전까지 성과가 잘 보이지 않습니다.
  • 스프린트 리뷰·데모데이로 작은 진척을 자주 공유.

4핵심가치별 서비스개발실 전체 질문

‘열기 → 들여다보기 → 실천으로’ 순서입니다. 시간이 짧으면 가치마다 들여다보기 1개 + 실천으로 1개만 써도 됩니다.

열기누구나 가볍게 답할 수 있는 질문들여다보기우리 실의 실제 상황을 꺼내는 질문실천으로내일부터 할 행동으로 이어지는 질문

🚀 혁신

  1. 열기지난 1년 동안 “이건 바꾸길 잘했다” 싶은 일하는 방식이 하나 있다면?
  2. 들여다보기우리 실에서 같은 요청을 세 번 이상 처리한 일은 무엇이고, 왜 아직 그대로일까요?
  3. 들여다보기새 기술을 ‘신중하게 검토한다’는 우리의 기준은 무엇인가요? 재사용성·운영 부담·비용 중 무엇을 가장 먼저 볼까요?
  4. 실천으로AI 도구로 일하는 방식이 바뀐 경험이 있나요? 실 전체가 함께 써볼 만한 것은?
  5. 실천으로운영 요청이 몰리는 와중에 개선·실험 시간을 지키려면 무엇이 필요할까요?

🌱 배려

  1. 열기동료의 설명 덕분에 어려운 내용을 쉽게 이해했던 순간이 있었나요?
  2. 들여다보기고객이나 다른 부서의 요청을 거절해야 할 때, 어떻게 말하면 배려가 될까요?
  3. 들여다보기다른 파트(기획·인프라·수집·개발)의 일 중 내가 잘 몰라서 부담을 줬을 수도 있는 것은?
  4. 실천으로내 작업이 다른 사람 일정에 영향을 줄 때, 언제·어떻게 미리 알리면 좋을까요?
  5. 실천으로다음 담당자를 위해 남기는 것(문서, 주석, 인수인계)의 최소 기준을 정한다면?

🤝 신뢰

  1. 열기“이 사람 말이면 믿는다” 싶은 동료들의 공통점은 무엇인가요?
  2. 들여다보기일정 지연은 ‘확실해졌을 때’와 ‘가능성이 보일 때’ 중 언제 공유하는 게 맞을까요?
  3. 들여다보기장애가 났을 때 우리는 ‘누가’보다 ‘무엇이’에 집중하고 있나요? 그렇지 않다면 무엇이 그렇게 만드나요?
  4. 실천으로고객이 문제를 우리보다 먼저 발견한 적이 있다면, 어떻게 하면 우리가 먼저 알 수 있을까요?
