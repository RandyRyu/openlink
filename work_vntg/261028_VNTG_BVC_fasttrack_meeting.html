Part A

DataForge 및 VNTG 사업

A1. 현장 근황 — 창원 설비 연동 검토

00:00~01:57
  • 창원 쪽에서 신규 설비가 들어오면서 DataForge 연결이 가능한지 확인해 달라는 요청이 많음
  • 설비 자체를 검증하는 것이 아니라 DataForge와의 연동 가능성을 프로토콜 단위로 검토하고, 필요하면 장비를 직접 확인
  • 상반기에 검토는 끝났으나 설치 일정을 몰랐고, 11월이 되자 연말 전에 설치가 몰리는 상황
  • 베스틸도 같은 방식으로 작업 중

A2. DataForge 패키지화 TF

01:57~04:26
  • TF 주간회의는 현재 3회차까지 진행
  • 구성: TF장이 메인 이름 확인 필요, 서비스개발실에서는 나와 동료 1명, UI 서비스 기획·개발 담당자가 참여
  • 목표: DataForge를 세아 외 고객에게도 판매할 수 있도록 상품화할지 결정
  • 배경: 원래 동국제강(경부제강) 건을 계기로 시작했고, 그 건이 무산된 뒤에도 "그래도 있어야 한다"는 초기 목표에 따라 계속 진행 고객명 확인 필요
  • 현재 상태
    • 데이터 수집·저장 부분은 완성
    • 연말까지 기본 틀을 갖춘 패키지 형태로 나올 예정
    • 부족한 것은 서비스 부분 — 고객이 "이걸로 뭘 할 수 있는데?"라고 물을 때 보여줄 활용 서비스가 있어야 함
  • AI까지 붙이려면 MDM이 먼저 갖춰져야 서비스가 됨

A3. MDM · 온톨로지 · 표준화 — AI 활용의 전제

04:35~07:39

VNTG가 제공할 수 있는 범위

  • 물리적 관계 정보(설비·장치 간 연결)는 VNTG가 알고 있으므로 온톨로지를 만들 수 있음
  • 업무 정보는 VNTG가 만들 수 없음 → 고객에게 제시하고 확정받는 방법을 서비스로 만드는 것을 고민 중
  • 창원·베스틸 기준으로 온톨로지 기본 틀까지 제공하는 것이 VNTG의 한계로 보고 있음

"MDM 없어도 된다"는 착각

  • 크리스탈 님이 데이터 에이전트 시연 때 겪은 일: MDM 담당자가 "AI가 있으면 MDM이 없어도 되느냐"고 질문
  • 두 사람의 공통 의견: 표준이 정의되어 있어야 사용자가 자유롭게 질문해도 AI가 거기에 대입해 답할 수 있다. 관계 정보가 있어야 함

표준화 방식

  • 국제표준에 나온 정보를 기준으로 정리
  • 설비는 납품 시 받는 스펙 문서(PDF·사진)를 업로드하면 AI가 필요한 정보를 추출해 등록하는 방식
  • 설비는 제조사가 정한 것이 곧 표준
  • 목표: 최대한 표준화·자동화해 시스템에 녹이는 것

A4. 다크팩토리와 추적성

07:39~13:30

크리스탈 님의 질문 — DataForge 고객은 무엇을 분석하나?

  • 크리스탈 님이 POC에서 경험한 것: MES 현업과 SAP 현업의 관점이 크게 다름. 경영기획은 원가 기준 질문이 많고, 생산 현업은 분석적인 질문이 많음
  • POC는 L1·L2가 아니라 MES 테이블을 대상으로 했음
  • 답: DataForge 고객은 현장의 이슈를 해결하려고 씀

다크팩토리는 가능한가

  • 최종 목적은 다크팩토리(인력 최소화)이지만, 제철 공장에서 가능할지는 의문
  • 그보다 품질에 영향을 미치는 요소를 해결하는 것이 맞음
  • 이를 위해선 세세한 것까지 정리해야 함 → 체계화된 분석 자료 → 불량이 나왔을 때 역추적할 수 있는 구조

걸림돌

  • 시간 불일치: 트래킹도 시간이 맞지 않아 억지로 맞춰서 만든 상태
  • PLC 비표준: 국내 업체가 만든 PLC가 많아 주소 체계가 표준과 맞지 않는 경우가 많음
  • AI 기대치: "AI가 알아서 다 해줄 것"이라는 기대가 있지만, 그러려면 모든 정보를 넣고 수억 원을 계속 들여야 함 → 실질적 효율화가 안 됨

경영기획이 원하는 원가·마진 추적을 하려면

  • 조업 정보가 요약된 정보가 단계별로 모두 생성되어야 하고, 그 요약은 기초 정보를 다 알아야 가능
  • MES와 SAP 간 1:1 매핑이 안 되고 1:N, N:M으로 변한다는 이슈는 추적을 하지 않았기 때문
  • 최소 단위 추적이 핵심: 1번 로트의 1·2·3번, 2번 로트의 2·3·4번을 가져가 제품을 만들었다는 정보를 모두 남겨야 함
  • 절단 시에는 절단 사실, 앞부분인지 뒷부분인지, 길이, 분할·재투입까지 추적되어야 경영기획이 원하는 전체 추적이 가능

A5. 라이선스 체계 개편

13:30~20:01

AS-IS 문제

  • 태그 수 단위로 과금하다 보니 고객이 태그 추가를 꺼림
  • 공장이 늘어 태그는 계속 늘어나는데 비용은 올리지 못하고 있는 상태
  • 그동안 추가 개발을 거의 공짜로 해주고 그것을 라이선스에 녹여 왔는데, 고객은 그 라이선스가 비싸다고 함

To-Be 방향

항목내용
과금 기준태그 수 → 저장 용량 기반. 불필요한 태그는 빼고 새 태그는 자유롭게 추가
비용 수준현재의 절반 이하까지 인하 가능. 그 이하는 어려움
계기위에서 "반으로 줄이라"는 지시 — 수익은 크게 줄어듦
범위수집·저장·제공까지만 라이선스. 기존에 해주던 다양한 개발은 공수 기반으로 별도 과금
형태수집·저장·제공을 자동화한 패키지 + 기본 조회 서비스 제공. 태그 추가는 고객이 직접
판매 방식소스 판매가 아니라 이용(구독)형 — 끄면 끝나는 구조
인프라클라우드 기반이라 저장 용량 부담이 체감상 적음

시장 반응 기대

  • 싸고 쉽게 들어올 수 있으며, 클라우드에 올려 접속해 쓰는 구조라 신규 고객 유입에도 도움
  • 중소·중견기업, 그리고 경남 피지컬 AI 국책과제처럼 데이터 수집부터 해야 하는 곳에 수요
  • 현재 단가는 태그당 약 3,000~4,000원 수준 확인 필요 — 구매자에게는 단가만 보이고, 그 외에 제공하는 서비스는 설명하기 어려움

A6. 데이터 인프라의 가치 인식 문제

20:01~29:50

"공기·수도"처럼 여겨짐

  • 데이터를 공기나 수돗물처럼 자연스럽게 가져다 쓰면서도 "DataForge는 어디에 쓰는 거냐"는 말이 나옴
  • 데이터 산업의 기본은 수집·정제·보관·제공이고 그 위에서 모든 것이 돌아가는데, 너무 당연하다 보니 "이걸 왜 돈 주고 써야 하나"가 됨
  • 비유: 상하수도 시설 — "수도요금 안 내려면 물을 쓰지 마시라"는 이야기도 나옴

AX 성과 귀속 문제

  • 경영기획은 데이터 분석 경험자를 채용해 자체 대시보드를 만들었고, 시연 후 "현업은 금방 하는데 왜 이렇게 오래 걸리냐"는 질문이 나옴
    • 차이: 현업은 이미 정제된 데이터로 작업했고, VNTG 시연은 원천 데이터부터 AI로 문서화되지 않은 정보를 다룰 수 있는지 검증한 것
  • AX 임팩트 발표에서도 실제로는 VNTG가 뒤에서 데이터·가이드·백단을 지원했지만 그 부분은 빠지고 발표됨
  • 문제는 "그럼 꼭 VNTG가 없어도 되겠네"라는 공격을 받을 수 있다는 점

존재감이 드러나는 순간

  • 데이터가 끊기는 순간 바로 연락이 옴. 모니터링으로 먼저 알리기도 하지만 놓칠 때도 있음
  • DataForge와 인터페이스되는 시스템 리스트: 기존 것은 리서치로 정리했고, 패키지에서는 자동 생성되도록 만드는 중

경영진 설득 부족

  • 왜 필요한지 경영진이 이해할 수 있게 어필하는 것이 부족함 — MES는 이해해도, 그 아래 설비까지 연결된다는 것은 잘 전달되지 않음
  • 결국 디지털 트윈처럼 화려하게 연결된 것을 보여주는 방식이 가장 효과적일 수 있음
  • 어필이 제대로 안 되니 DataForge 예산을 늘릴 수 없고, 고객은 태그를 안 쓰기로 하고 줄이는 상황

A7. 태그 선별과 "분석 우선" 접근

26:50~29:50
  • 이 태그가 필요한지 아무도 정하지 못하는 것이 근본 문제. 현업도, 관련 팀도 모름
  • 현업도 "일단 이 태그 주세요"라고 하고, 1년이 지나도 그대로임 — 데이터는 필요하다고 생각하지만 어떻게 분석할지를 모름
  • 해법: 처음 시작은 분석이어야 함
    • 공장이 들어오면 일단 전부 수집하는 것은 맞음
    • 1년 동안 분석하며 불필요한 것은 빼고 중요한 것을 추려 정제
    • 1~2년이면 공장 전체에서 핵심 데이터만 보는 상태로 안정화
    • 그것으로 분석이 안 되는 것이 있으면 새 태그를 다시 확인 — "태그는 죽였다 살렸다 하는 것"

A8. 데이터 에이전트 POC 리뷰와 VNTG의 방향

45:40~53:29

크리스탈 님 POC 결과에 대한 의견

  • 결과는 동료를 통해 들었고 작업 방식도 확인함. 정형 데이터를 마운트한 것 외에는 VNTG가 적용했던 방식과 큰 차이가 없었음
  • 궁금한 점: 그래프(GQL) 부분이 어떤 결과를 줄지 — 관계 정보를 어떻게 매핑해 처리할지
    • VNTG 방식: 물리적 관계는 자동 생성하고, 유추한 관계는 고객에게 제시해 확정·수정하게 하는 구조
  • 크리스탈 님 측 경험
    • 정형 데이터부터 접근한 것이 특이하다는 평가를 받음
    • 그래프는 활용을 시도했으나 못 했음
    • 용어에 수식(예: 매출액 = SAP 계정 합계)을 넣었는데 반영되지 않음 → 원인은 한글 지원이 아직 모든 기능에 열리지 않은 것

시맨틱 레이어 자동화의 한계

  • 데이터와 코드에서 뽑을 수 있는 것(용어, 유의어 등)은 자동화가 가능
  • 업무 프로세스를 넣는 것이 가장 어려움 — 어디에 어떻게 넣어야 활용될지
  • BPM 얘기가 나오지만 실제로는 데이터화된 BPM이 없고, 현업 매뉴얼도 최신으로 업데이트된 것을 본 적이 없음
  • 그런데도 각자 경험대로 돌아가는 것이 신기할 정도

VNTG가 집중할 방향 — 두 사람 모두 동의

  • DataForge 내부적으로 LLM을 붙여 데이터 에이전트 기능은 이미 구현해 둔 상태이며, 테스트 결과도 POC와 차이가 없었음
  • 대신 공장 기준으로 MDM 정보를 자동 생성·분류하는 구조를 계속 만들고 있음 — 이게 탄탄하지 않으면 에이전트는 의미가 없음
  • 데이터 에이전트는 빅테크가 만든 것을 붙이면 되고 그쪽이 더 잘 만듦 → VNTG가 직접 개발할 필요는 없음
  • VNTG는 AI-Ready 데이터를 만드는 쪽에 집중하는 것이 맞다. 마스터 데이터를 어떻게 구성하고 분해하고 관리할지가 핵심
  • 오히려 그쪽이 시장성이 있을 수 있음 — 다들 하기 싫어하고, 어렵고, 도메인 지식이 반드시 필요한 영역
Part B

제조 현장과 IT 협업 구조

B1. 산업별 차이와 현장 문화

29:50~30:51 · 34:43~36:13
  • 반도체·화학은 미세한 변화가 제품에 큰 영향을 주기 때문에 모든 것을 정밀하게 따짐
  • 철강은 "대충 해도 비슷한 품질이 나온다"는 인식 → 작업 지시가 내려가도 조업자가 자기 방식대로 작업
  • 현재는 정해진 작업 기준을 따르도록 막는 작업을 하는 중
  • 조업은 하청이 많고, 현장 관리자도 실제 조업 방식을 모르는 상태 → 매뉴얼화·체계화가 안 되어 모르는 구간이 생기고 그것이 사고로 이어짐
  • 30~40년 경력자는 데이터를 보여줘도 "내가 맞다"며 자기 방식대로 함. 제품만 나오면 된다고 생각하고 품질은 자기 책임이 아님
  • 창원에도 계속 전하는 메시지: 조업 프로세스와 현업 업무 프로세스가 함께 변하지 않으면 결국 아무것도 안 된다

B2. 고객의 요구사항 정리 역량 부족

32:01~34:43
  • 고객의 가장 큰 문제는 요구사항을 정리하지 못하는 것
  • 요구정의서·기획서·프로젝트 설계서 양식을 PPT 4~5장으로 만들어 줘도 채우지 못하고 "뭘 써야 되지?"에서 멈춤
  • 원인: IT를 하청으로 보는 인식 — "네가 알아서 다 해"
    • DT를 해도 업체를 불러 PLC를 도입하고 알아서 돌리면 된다는 식
    • 그것이 자기 업무에 어떤 영향을 미치는지는 생각하지 않음
  • 제조 현장에 들어가는 AI 업체가 힘든 이유
    • 영업으로 들어가는 것은 되지만 이후 3~4년을 버티다 계속 적자를 보고 나오는 경우가 대부분
    • 4~5년을 버텨야 그나마 모델이 되고 예측 대응이 가능해짐 — 사실상 IT 업체가 현장을 배우는 학습 기간
    • 현장은 스스로 문제를 풀려고 하지 않고, 일자리 위협으로 느껴 협조하지 않기도 함

BVC와의 연결 (나의 의견)

  • 고객이 "이런 걸 하고 싶다"는 시작점만 주면, VNTG가 설비와 보유 데이터를 하나하나 확인해 구현 가능한 기안을 만들어 줌
  • 고객은 상세 기안을 만들지 않으므로 기안부터 설계·개발·서비스 오픈까지 VNTG가 다 함
  • 이것이 곧 BVC가 아닌가 생각함

B3. 계약 구조 개선 제안 (크리스탈 님)

36:13~38:53
  • 직원들의 고민: 열심히 AI와 BVC를 해도 고객이 "AI 했으니 알아서 하라, 더 싸게 해 달라"고 나올 수 있음 → 고객이 바뀌지 않는 상황에서 보람을 느낄 수 있을까
  • 첫 고객에게는 효용 증명을 위해 무료나 레퍼런스 차원으로 해줄 수 있지만 계속 그럴 수는 없음
  • 현재 MS(유지보수) 구조의 문제: 같은 대가에 더 많은 것을 요구받음 → VNTG는 더 해줄 이유가 없고 고객은 더 시키려 함
  • 제안: 계약을 완전히 분리
    • 시스템 가용성 보장, 일반 장애 대응, 정기 점검 → 기본 운영 계약
    • 추가 요청 → SR 기준 계약 (많이 하면 많이 받고, 적게 하면 적게 받음)
  • 기대 효과: 돈을 내야 하면 불필요한 요청이 줄고, 직원 사기도 올라감
  • 공감대: IT 업계 전체의 이슈

C1. 참여 확인과 프로그램 구조

  • 서비스개발실에서 2명이 참여한 것을 크리스탈 님이 매우 반겼음. Stage 1 때도 좋은 사례를 많이 적어줘서 고마웠다는 언급
  • 전체 참여 예상 인원은 약 15명. 중간·주니어급은 반드시 면담 — 실제로 지목당한 경우가 꽤 많음

단계별 차이

단계내용
Stage 2사례 하나를 정리
Stage 3사례 하나 + 그 과정의 방법을 다른 사람도 활용할 수 있게 방법론화 + 스킬 준비
  • 가장 부담스러워하는 부분은 사례를 수치로 증명하는 것
  • 일부 참여자는 "위에서 인정해주지 않으면 이야기하기 어렵다"는 의견도 있었음 → 크리스탈 님은 그냥 의견 교환으로 진행하면 된다는 입장. 신입사원의 의견이 더 도움이 될 수도 있음
  • 교육은 직급과 상관없이 필요해 보여 준비한 것
  • BVC는 정해진 프로그램이 아니라 만들어가는 프로그램 — 필요한 지원이 있으면 말해 달라, 반영하겠다
  • 시간은 너무 많이 뺏지 않도록 할 예정

Stage 3 이후의 역할 역할명 확인 필요

  • Stage 2를 전사로 오픈하면 Stage 3 이수자가 최대 2~3명을 담당

사례 선정 기준

  • Stage 1에서 했던 사례를 심화해도 되고, 새로 해도 됨
  • 과거 프로젝트도 가능 — 작년 사례, 올해 초 사례 모두 가능
  • 개인 사례가 아니어도 됨 — 팀 사례, 협업 사례 모두 가능. 전 직장 사례도 가능하나 가급적 현 회사 사례
  • 실패 사례도 충분히 가능
  • 가장 좋은 사례: 거기서 사용한 방법을 다른 사람에게 공유하면 도움이 될 만한 것
  • 예시: 과거 프로젝트 중 문제 정리가 잘 되어 제안이 잘 된 파트를 중심으로 정리

나의 반응

  • 6주 안에 끝날 제안이 뭐가 있을지 생각하면 쉽지 않다고 느꼈으나, 과거 사례를 활용하면 부담이 없을 것 같음
